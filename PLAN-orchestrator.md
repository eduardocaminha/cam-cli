# Plan — cam orchestrator + Linear integration

Status: **proposal** — to be broken into PRDs and implemented iteratively.

---

## Goal

Transform `cam` from a collection of independent commands into a single
interactive agent (the **orchestrator**) that is the only human-facing
interface for a project. The orchestrator:

- Lives in the tmux window spawned by `cam init`.
- Holds a persistent, long-lived context about the project across work cycles.
- Spawns `/cam-*` workers as fresh, short-lived sessions to do actual work.
- Absorbs structured outputs from workers back into its own context.
- Integrates with Linear as the source of truth for issues and cycles.

The individual `/cam-*` commands continue to exist as workers but are **never
invoked directly by the human** — only by the orchestrator.

---

## Mental model

```
┌───────────────────────────────────────────────────────┐
│ tmux window spawned by `cam init`                     │
│                                                       │
│  ┌──────────────────────────┬──────────────────────┐  │
│  │ Pane 0: orchestrator     │ Pane 1: menu/status  │  │
│  │ (claude, long-lived)     │ (key hints)          │  │
│  │ — you talk to it         │                      │  │
│  │ — it spawns workers      │                      │  │
│  └──────────────────────────┴──────────────────────┘  │
└───────────────────────────────────────────────────────┘
                      │
                      │ spawns fresh claude subprocesses on demand
                      ▼
       /cam-issue    /cam-plan    /cam-next    /cam-review   /cam-ship
       (fresh)       (fresh)      (fresh loop) (fresh)       (fresh)
```

The orchestrator never reads code. Workers read and write code.

## Lifecycle

### 1. `cam init` (one-shot, existing flow)

Already implemented. After stage 2 finishes, the config agent writes a
handoff note and exits. The tmux window then **transitions** to the orchestrator:

- Pane 0 replaces the config agent with the orchestrator session.
- Pane 1 menu updates to reflect orchestrator key bindings.
- The orchestrator starts with the config handoff as its first context.

### 2. `cam run` (long-lived, new)

The entry point for returning to an existing project. If the tmux session
already exists → `tmux attach`. Otherwise → spawn a new tmux window with the
same orchestrator layout, hydrated from the project state files.

### 3. `cam reconfig` (one-shot, new)

Variant of `cam init` for existing projects that need re-configuration
(stack changed, conventions updated, new external services). Runs the config
agent with a flag indicating it's a reconfig, not an initial setup. On exit,
hands off to the orchestrator which absorbs the delta.

---

### cam-cli produces its own rules, docs, and visual assets

The reporter has `.claude/rules/`, `.claude/skills/`, and design-system assets
that are **reporter-specific** — they must NOT be vendored into cam-cli
templates. Instead, cam-cli is responsible for producing these artifacts
**for each project it manages**.

**What this means in practice:**

- During `cam init` stage 2, the config agent can create a project-specific
  `.claude/rules/` directory with files like `api.md`, `testing.md`,
  `components.md` — but the *content* is inferred from the project's stack,
  not copied from reporter.
- Same for skills: if the project needs a `SKILL.md` (e.g. debugging
  patterns, domain-specific playbooks), the orchestrator or config agent
  creates it with actual content for that project.
- Visual assets (design tokens, component previews, documentation sites):
  when a project needs them, the orchestrator can spawn a worker that
  generates them from scratch based on the project's existing code and
  design system.
- cam-cli ships **formats and conventions** (frontmatter schemas, directory
  layout, the `SKILL.md` pattern), not **content**.

**Implementation note for templates/:**

- The `templates/` directory in cam-cli holds generic scaffolds only.
- Project-specific content is generated by agents at runtime (during init,
  reconfig, or on-demand through the orchestrator).
- If a new pattern emerges (e.g. "every project should have a
  `.claude/rules/testing.md`"), the fix is to update the generic instructions
  given to the config agent — not to vendor a specific testing.md into cam-cli.

## Orchestrator responsibilities

### Hold persistent project context

The orchestrator's system prompt includes, in order of importance:

1. **Project identity** — stack, conventions, domain (from `CLAUDE.md`).
2. **Issue system config** — `linear` | `github` | `none` (from `cam init`).
3. **Journal** — `scripts/cam/journal.md`, one entry per cycle:
   - Cycle ID (branch name or Linear issue)
   - What was planned, what shipped, what got stuck
   - Key decisions and their rationale
4. **Current state** — `prd.json`, `handoff.json`, current branch.

The orchestrator never loads source code into context. For code questions it
dispatches a worker with `Read`/`Grep`/`Glob` tools.

### Talk to the human in natural language

You say things like:

- *"o que temos pra fazer esse ciclo?"* → orchestrator queries Linear, lists
  issues in the active cycle sorted by priority.
- *"implementa o LIN-42"* → orchestrator fetches LIN-42 details, spawns
  `/cam-plan` with issue context, waits for PRD approval, spawns `/cam-next`
  loop, updates LIN-42 status.
- *"tá travado no middleware, ajuda"* → orchestrator recalls from journal
  that a similar block happened in LIN-28, summarizes the fix, suggests the
  approach for the current case.
- *"ship"* → orchestrator spawns `/cam-ship`, updates Linear to Done.

### Dispatch workers

Workers are invoked with `claude --print --permission-mode bypassPermissions`
so they exit cleanly and return structured output (status lines, `handoff.json`).
The orchestrator:

1. Prepares the worker's prompt (injects issue ID, round number, etc.).
2. Spawns the worker as a subprocess.
3. Tails output in pane 1 (or a dedicated worker pane).
4. Parses exit status and result files.
5. Absorbs the result into its own context via a concise summary appended
   to the journal.

### Update Linear

- On `/cam-plan` completion → set issue status to *In Progress*.
- On `/cam-ship` completion → set issue status to *Done*, add PR link as comment.
- On failure or abort → leave a comment with what happened and stays *In Progress*.
- When the human asks for status → query Linear live, don't rely on cached state.

## Linear integration

### Config (set during `cam init`)

New questions in the stage 2 wizard:

```
Which issue system does this project use?
  (1) Linear
  (2) GitHub Issues
  (3) None (local only)
```

If Linear:

```
Linear API key (from linear.app/settings/api):
Linear team key (e.g. ENG, PROD):
```

Stored in `~/.config/cam/config.toml` (global, not per-project — one Linear
workspace per user typically) plus `.cam/project.toml` (team key + project ID).

### Auth

Use the `Linear-API-Key` HTTP header with the user's personal API key. No
OAuth flow for v1 — the user pastes the key during `cam init`.

### Operations the orchestrator needs

| Operation | Linear GraphQL |
|---|---|
| List issues in active cycle | `cycles(filter: { isActive: { eq: true } }) { issues }` |
| Get issue details | `issue(id: ...) { title, description, priority, ... }` |
| Update issue status | `issueUpdate(id, input: { stateId })` |
| Add comment | `commentCreate(input: { issueId, body })` |
| Create issue (for `/cam-issue`) | `issueCreate(input: { teamId, title, ... })` |

### `cam-issue` rewrite

Current `/cam-issue` is GitHub-specific. Rewrite as a dispatcher:

- If `issue_system = linear` → create in Linear, return Linear issue ID (LIN-42).
- If `issue_system = github` → current behavior.
- If `issue_system = none` → generate a local issue ID (CAM-42).

The PRD schema's `issueNumber` field becomes `issueId` (string, not number)
to accommodate all three.

## What changes in existing files

### New files

- `src/commands/run.ts` — opens/attaches the orchestrator tmux window.
- `src/commands/reconfig.ts` — variant of init for existing projects.
- `templates/agents/subagent-orchestrator.md` — the orchestrator system prompt.
- `src/linear/client.ts` — thin GraphQL client for Linear.
- `templates/scripts/cam/journal.md` — empty template with format docs.

### Modified files

- `src/commands/setup.ts` (from `cam init`):
  - Add Linear config prompts.
  - After config agent exits, transition pane 0 to the orchestrator.
- `templates/commands/cam-issue.md` — dispatch on `issue_system`.
- `templates/commands/cam-plan.md` — accept Linear issue ID, not just `#N`.
- `templates/commands/cam-ship.md` — call Linear `issueUpdate` on completion.
- `index.ts` — register `cam run` and `cam reconfig`.

### Unchanged

- Workers (`cam-next`, `cam-review`, subagents) — these stay fresh-session.
  They don't need Linear themselves; the orchestrator does all Linear I/O
  before and after worker invocations.

## Open questions (to resolve before implementation)

1. **Where does the orchestrator live when the tmux window is closed?**
   - Option A: orchestrator dies with the window; `cam run` always starts fresh
     but reads the journal on boot to rehydrate.
   - Option B: orchestrator session persists via `claude --session-id`, and
     `cam run` resumes it.
   - Option A is simpler and arguably more robust (no stale context between
     weeks of inactivity).

2. **Journal size management.**
   - The journal grows unbounded. When it gets large, does the orchestrator
     summarize old entries? Archive them? Just keep reading?
   - Likely: summarize entries older than N cycles into a compact project-
     history block at the top of the journal.

3. **How does the human interrupt a running worker?**
   - The orchestrator spawns a worker and waits. If the human wants to stop
     it mid-flight, the pane 1 menu needs a `kill current worker` key.
   - The worker exits, orchestrator absorbs whatever partial output exists,
     and returns to human prompt.

4. **Should workers be able to ask the orchestrator questions?**
   - Today workers are fully autonomous (no `AskUserQuestion` tool).
   - Could be useful: worker hits ambiguity, emits `ASK_ORCHESTRATOR: ...`,
     orchestrator surfaces it to human, relays answer back.
   - Adds complexity; defer to v2.

5. **Multiple concurrent projects?**
   - v1: one orchestrator per project, running in its own tmux session named
     after the project. `cam run` in a different cwd opens a different session.

## Implementation phases

### Phase 1 — foundation (no behavior change for current users)

- [ ] Add `issue_system` prompt to `cam init` wizard.
- [ ] Build `src/linear/client.ts` (minimal: list cycles, get issue, update
      issue, create comment).
- [ ] Add `journal.md` template.
- [ ] Rewrite `templates/commands/cam-issue.md` to dispatch on `issue_system`.

### Phase 2 — orchestrator MVP

- [ ] Write `templates/agents/subagent-orchestrator.md` system prompt.
- [ ] Implement `cam run` — spawns claude with the orchestrator prompt in
      pane 0, hydrates context from project files.
- [ ] Update `cam init` stage 2 to transition pane 0 from config agent to
      orchestrator after setup.
- [ ] Verify: human can ask "list issues in cycle" and orchestrator queries
      Linear, renders list.

### Phase 3 — orchestrator drives workflow

- [ ] Orchestrator can spawn `/cam-plan` and absorb the resulting `prd.json`.
- [ ] Orchestrator can spawn `/cam-next` in a loop and track progress.
- [ ] Orchestrator updates Linear status on plan/ship transitions.
- [ ] Journal entry is appended on every cycle completion.

### Phase 4 — polish

- [ ] `cam reconfig` command.
- [ ] Worker interrupt key in pane 1.
- [ ] Journal summarization when > N cycles.
- [ ] Optional: worker → orchestrator questions protocol.

### Phase 5 — visual polish

Everything the human sees should feel deliberate, not utilitarian.

- [ ] **Brand pass on every human-facing surface**:
  - `cam init` stage 1 + stage 2 output (printSuccess/printWarning/printError).
  - Menu pane (pane 1) — consistent color palette, proper box drawing.
  - Orchestrator pane startup banner.
  - Error screens.
- [ ] **Menu pane polish**:
  - Replace the current `printf` blob with a proper TUI (status header,
    key hints footer, live worker state in between).
  - Live-update worker state via `tmux pipe-pane` without repainting the
    whole pane.
- [ ] **Orchestrator pane startup banner**:
  - Show project name, current cycle, open issues count, last journal entry
    at a glance when the human attaches.
- [ ] **Consistent typography and color tokens**:
  - Extend `src/logging/color.ts` with semantic tokens
    (`cam.accent`, `cam.muted`, `cam.critical`) used everywhere.
- [ ] **Transitions**:
  - When `cam init` ends and the orchestrator boots, show a short
    visible transition (e.g. "project configured — orchestrator ready")
    instead of a jump-cut.

### Phase 6 — robust independent dashboard

The dashboard must be a first-class, standalone view — openable and
closeable at any time without affecting the orchestrator or workers.

- [ ] **Detach from the init tmux window**:
  - Dashboard gets its own tmux window (or separate session) so closing it
    does not kill anything.
  - `cam dashboard` can be run at any point from any terminal — it
    attaches to the existing view or creates one.
- [ ] **Resilience**:
  - Survives: missing files (no `prd.json` yet), corrupt JSON, partial
    writes from workers, window resize, Ctrl+C.
  - Falls back to a clear "nothing happening yet" screen instead of crashing.
  - Re-reads state files on a ticker — picks up new workers automatically
    without restart.
- [ ] **State consolidation**:
  - Single source of truth: reads from `prd.json`, `handoff.json`,
    `journal.md`, and the orchestrator's worker log.
  - Derived views: current worker, last 10 journal events, cycle progress
    bar, Linear issue summary (if configured).
- [ ] **Open/close semantics**:
  - `cam dashboard` — open/attach.
  - Close with `q` or terminal close — leaves the tmux dashboard window
    alive in the background, not the process.
  - `cam dashboard --stop` — fully tear down the dashboard window.
- [ ] **Multi-instance safe**:
  - Can be open in two terminals at once (e.g. laptop + desk monitor) —
    both render the same state, both stay in sync.
- [ ] **No writes**:
  - Dashboard is strictly read-only. All mutations go through the
    orchestrator. This guarantees it can be killed or restarted without
    risk of state corruption.

## Non-goals (explicitly not in scope)

- Replacing `cam next` loop semantics — the fresh-session-per-iteration
  discussion is orthogonal and can be done independently.
- Multi-user / shared orchestrator state (Linear is the shared layer).
- Voice / web UI — terminal only, at least for v1.
- Obsidian integration — deferred, not needed while journal + CLAUDE.md suffice.
