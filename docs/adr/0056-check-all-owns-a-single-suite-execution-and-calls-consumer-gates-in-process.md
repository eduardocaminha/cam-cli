# ADR 0056: check-all owns a single suite execution and calls consumer gates in-process

## Context

scripts/check-all.ts ran 14 gates through one uniform path: each gate is a flat {name, cmd, args} row spawned with fully inherited stdio, so no gate output is ever captured and no state is shared between gates. Three of those gates each executed the full test suite. The `test` gate ran `bun test`; the `coverage` gate spawned scripts/check-coverage.ts which internally ran `bun test --coverage`; the `skip-ratchet` gate spawned scripts/check-skip-ratchet.ts which internally ran `bun test`. One check:all therefore cost three full suite executions where one suffices, measured at roughly 400s against roughly 134s. The recorded gate-results.json carries the fingerprint: gate `test` at 34511ms against gate `coverage` at 34381ms, near-identical durations, meaning coverage paid for a fresh run instead of reusing one. The cost recurs on every worker story and every reviewer round. In the CAM-482 review it consumed about 22 percent of the 30 minute review budget in pure redundancy, contributing to the ceiling being hit five times without a verdict.

## Decision

check-all performs one `bun test --coverage`, captures its combined output, and feeds the two consumer gates in-process by calling their exported entries with that output injected, rather than spawning them as subprocesses. The dependency injection seams already existed and were built for this: GetSuiteOutputFn is raw-string typed, parseCoverageOutput is exported and pure, and scripts/test-in-container.ts was already feeding pre-captured output to the skip checks without a second run. The alternative considered and rejected was an inter-process form, where check-all writes the captured output to a temporary file and advertises the path through an environment variable that each consumer script reads when present and otherwise falls back to spawning its own suite. That form preserves manifest uniformity and the standalone script contract without any change to check-all's gate model, which is its genuine advantage. It was rejected because the fallback path is the defect: a collapse that can silently degrade back into re-spawning, or read a stale artifact from a crashed earlier run, can ship inert while a token-presence oracle still reads satisfied. This project has already shipped exactly that failure once, where a detector was overwritten on every call and returned still-working forever while two acceptance criteria asserting the wiring read as satisfied. The in-process form removes the entire class by construction, because there is no fallback to degrade into and no artifact to go stale: the output either exists in memory for the lifetime of one invocation or the run failed.

## Consequences

The flat gate manifest stops being uniform. Two of the 14 gates are no longer plain subprocess spawns, so the Gate model must express both shapes, the per-gate cmd and args assertions in test/check-all.test.ts must be restated rather than deleted, and scripts/check-all.ts needs its file-size ceiling of 176 raised with a tracker ref. Capturing the suite output is a type-level change, since the SpawnFn type bakes the inherit generics in and the test fakes depend on them, and the operator's live progress must be teed rather than swallowed. Gate identity is preserved deliberately: all three gates keep their names, their independent rows in gate-results.json, and their own failure conditions, so the CI step-summary table and the ci-parity gate are unaffected. Standalone invocation of either consumer script keeps spawning its own suite, which is correct for standalone use and means the redundancy is removed only where it was actually being paid. The fourth suite execution, in the CI container lane, is out of scope and remains. One coupling is created and must be watched: the collapsed run's exit code now carries the `test` gate verdict, which is sound only while no coverage threshold exists. There is no bunfig.toml today and a deliberately failing test exits 1 identically with and without the coverage flag, but adding a coverage threshold later would re-couple the coverage and test gates.
