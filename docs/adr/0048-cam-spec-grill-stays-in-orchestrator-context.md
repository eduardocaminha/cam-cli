# ADR 0048: cam-spec grill stays in the orchestrator context

## Context

CAM-197 is the epic titled "every cam command is deterministic CLI or a spawned pane with structured handback; orch only converses, decides, narrates" (`scripts/cam/issues/CAM-0197.json`). Its own framing text proposed a Layer 3 for the `/cam-spec` grill (the operator-interactive interview run by the spec-with-docs skill chain, `.claude/skills/spec-with-docs/SKILL.md`, driven from `.claude/commands/cam-spec.md`): "cam-spec grill moves to its own pane with handback (interview transcript has zero value to the long-lived orch context after the spec lands on main; a 50k-token grill inside the orch contradicts the one-PR-per-session invariant)." The epic explicitly flagged this as ADR-worthy and deferred the actual resolution to a grill of the epic itself.

That grill happened on 2026-07-22 and reached the opposite conclusion from the epic's own framing text: the grill stays in the orchestrator context. This ADR records that decision and the reasoning that overturned the epic's initial premise, so the CAM-197 epic's remaining Layer 1 and Layer 2 slices are framed by a settled Layer 3 answer instead of carrying it forward as an open question into every future slice.

The two prior Layer 1/Layer 2 precedents already shipped establish the boundary this ADR sharpens. `cam issue close`/`abandon` (CAM-210) and `cam spec --persist` (CAM-213, the deterministic writer `specifyIssueOnMain` invoked from the final step of `.claude/commands/cam-spec.md`) moved non-interactive, LLM-free mutations out of the orchestrator's inline execution into pure CLI subcommands. `cam-review` orchestration (still inline per the CAM-197 description) is LLM-needing but non-interactive: it already runs the reviewer subagent in a spawned pane with a structured handback (`worker-report.json` plus a one-line `send-keys` push, the CAM-75/77/78 comms decision, `src/supervisor/review.ts`). Neither precedent involves a human answering questions turn by turn. The grill does.

## Decision

The cam-spec grill stays in the orchestrator context. It does not move to a dedicated pane.

The orchestrator/worker boundary this epic draws is at LLM-non-interactive work, not all LLM work. A spawned pane with structured handback (`worker-report.json`, `review-report.json`, the `CAM_*_STATUS` sentinel convention) is the right shape for work an autonomous agent can complete unattended and report back on: deterministic CLI calls (Layer 1) and LLM work with no human turn-taking (Layer 2, e.g. the reviewer). The grill is neither: it is a live, multi-turn conversation where the operator answers questions one at a time and the orchestrator's next question depends on the prior answer (per `.claude/skills/grilling/SKILL.md`: "Ask the questions one at a time, waiting for feedback on each question before continuing"). There is no handback contract to write, because there is no point at which a worker pane can complete and report: the human is the completion signal, at every turn, for the whole interview. Piping that turn-by-turn exchange through a spawned pane would mean the orchestrator relays every question and every answer across a pane boundary it does not need, in exchange for no reduction in operator involvement and no autonomy gained: the human is in the loop for the entire interaction either way. The orchestrator remains the single human-facing interface for the whole cam-cli session (`cam run`, per the CAM-55 single-hub decision); a second, spec-only interactive surface would fragment that interface for a case that gains nothing from the split.

This decision is recorded as an ADR because it clears the standard three admission gates:

1. **Hard to reverse.** It redefines the epic boundary that CAM-197's own framing text originally drew (the boundary was "orch only converses, decides, narrates," which read literally would put every multi-turn human exchange, including the grill, in-scope to move out). Every future CAM-197 slice, and any future skill that wants operator interaction, now inherits this line instead of re-deriving it.
2. **Surprising without context.** It contradicts the literal "orch only converses" reading of the CAM-197 title, and it directly reverses the epic's own Layer 3 proposal text quoted above. A reader who only sees the epic description would reasonably expect the grill to be Layer 3 pane work; without this ADR, that expectation is wrong and undocumented.
3. **Genuine trade-off, not a free win.** The alternative (a dedicated grill pane) was seriously considered by the epic itself, and each side has real cost: a pane preserves orchestrator context at the price of splitting the operator's single human-facing interface across two surfaces for the one workflow where every turn needs the human anyway; staying in-context keeps one interface at the price of the interview's token cost living, for the duration of the interview, inside the orchestrator's own context window.

## Consequences

The token cost of the grill is real but bounded and non-cumulative. A `/cam-spec` interview can run to roughly 50k tokens inside the orchestrator's context, but that cost is shed at the next cycle-close recycle: once the assembled spec is piped into `cam spec --persist <id>` (the deterministic writer, `specifyIssueOnMain`) and the issue lands on main as `stage:specified`, the interview transcript has zero further value to the orchestrator. The orchestrator's own cycle-close handoff and recycle path (`buildOrchestratorPaneCommand` in `src/commands/run.ts`, the `--cycle-close` marker consumed by `recordCycleTokens` in `src/commands/journal.ts`) already tears down and rehydrates orchestrator context between cycles, so the grill's token spend is confined to the single PR cycle the spec produced and does not accumulate into subsequent cycles. This is why the grill does not violate the one-PR-per-session invariant the epic's own framing text worried about: that invariant is about a session's committed diff spanning more than one PR, not about a bounded, self-clearing interview cost inside one session's context window.

No pane-based grill contract needs to be designed, documented, or maintained: there is no `worker-report.json` equivalent to define for an interactive interview, and no risk of the CAM-75/77/78 "never parse pane scrollback" rule being violated by a grill-in-a-pane implementation, because no such implementation exists. The remaining CAM-197 Layer 1 and Layer 2 slices can proceed against a settled Layer 3 answer: any future skill that is genuinely LLM-non-interactive (no per-turn human answer required) is a Layer 1/2 candidate for pane-plus-handback extraction; any skill that is a live operator interview, like the grill, stays in the orchestrator context by this precedent.
