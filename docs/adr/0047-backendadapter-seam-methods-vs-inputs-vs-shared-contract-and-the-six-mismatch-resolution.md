# ADR 0047: BackendAdapter seam: methods vs inputs vs shared contract, and the six-mismatch resolution

## Context

ADR-0046 recorded the headline decision for CAM-54 (spike-first, per-subagent, adapter at the report/sentinel boundary) but left the adapter's internal shape and the six claude/codex mismatches unresolved at the level of concrete surface. Before any codex dispatch code lands, this fuller design spike must state, per mismatch: whether it becomes an adapter METHOD (a function every backend implements differently), an adapter INPUT (a parameter threaded through one shared method), or a SHARED CONTRACT (identical behavior across backends, owned outside the adapter entirely). Getting this split wrong invites either an adapter with one method per config knob (INPUT masquerading as METHOD, CAM-54 gotcha risk) or backend-specific logic leaking into the shared supervisor loop (SHARED CONTRACT masquerading as backend-specific).

The four worker actors (implementer, planner, auditor, reviewer) each already have a pure argv builder with an identical shape: `worker-argv.ts` (`buildImplementerWorkerArgv`), `plan-argv.ts` (`buildPlannerWorkerArgv`, `buildAuditorWorkerArgv`), `review.ts` (`buildReviewerWorkerArgv`). All four:

- start with `workerEnvPrefix(isolation)` (an `env -u ...` strip, shared, CAM-43);
- run `claude --permission-mode <mode> --session-id <uuid> --model <model> --agent <agentName> '<prompt>'`;
- are pure functions (no I/O), single-quote-escaping the prompt;
- resolve `model` from `readPhaseModel(phase)` (per-phase, `src/config/models.ts`) at the call site, not inside the builder.

`readBackend` (`models.ts:171-191`) is currently a single top-level key (`DEFAULTS.backend = 'claude'`); CAM-53 shipped this plus an informational, non-blocking guard (`CODEX_GUARD_NOTICE`, `spawn-resolution.ts:60`) that fires when `backend === 'codex'` but still spawns claude. Completion detection is polling-based: the supervisor (`loop.ts`) tails the last 10 lines of `capture-pane` for a `CAM_*_STATUS` sentinel, or (when a report path is wired) reads `worker-report.json` / `review-report.json` through the shared hand-rolled guard (`report-parse.ts`, ADR-0038). The per-worker token ceiling (`loop.ts:1189`, CAM-5) reads cumulative spend via `readWorkerTokens(uuid)`, which resolves a `.jsonl` transcript path for the session uuid and parses claude's own usage shape (`src/transcript/usage.ts`): this is claude-transcript-shaped and has no codex equivalent yet.

## Decision

### The seam: one concrete adapter method, everything else is an input

`BackendAdapter` exposes exactly **one** concrete method for the worker-spawn seam:

```ts
buildSpawnArgv(actor: WorkerActor, opts: SpawnArgvOptions): string
```

where `actor` is `'implementer' | 'planner' | 'auditor' | 'reviewer'` and `opts` carries every value that today varies per call site: `model`, `agentName`, `permissionMode`, `uuid`, `taskPrompt`, `isolation`. **The env-unset prefix is an INPUT to this method, not a separate adapter method or a separate concern**: it is rendered by the adapter alongside the rest of the argv string, backend-conditional (claude's `workerEnvPrefix` list is claude-specific; a codex adapter renders its own env-strip list, if any, inside the same call). Concretely this replaces four near-identical exported functions (`buildImplementerWorkerArgv`, `buildPlannerWorkerArgv`, `buildAuditorWorkerArgv`, `buildReviewerWorkerArgv`) with one adapter method parameterized by actor, closing the CAM-54 gotcha risk of one-method-per-config-knob.

This resolves mismatch **(a) spawn-argv/seam**: `buildSpawnArgv` is the adapter method; `model`, `agentName`, `permissionMode`, and the env-unset prefix are inputs to it, not methods of their own.

Mismatch **(f) model-id namespace** is also an INPUT, not a method: codex ids populate the same per-phase `model` slot that `readPhaseModel(phase)` already resolves today. `readBackend` is upgraded from a single top-level key to a per-phase accessor (mirroring `readPhaseModel`), and the resolved `{phase, backend}` pair is what selects WHICH adapter's `buildSpawnArgv` is called; the model string itself is opaque to the adapter (tier-alias namespace for claude per ADR-0034, a different namespace for codex) and is threaded through as a plain input, never validated or interpreted inside the adapter.

Mismatch **(e) permission/sandbox+env** is a METHOD-shaped concern realized as adapter-internal behavior inside `buildSpawnArgv`, not a caller-visible method of its own: each backend's adapter renders its own permission/sandbox flags and env-strip list from the shared `permissionMode` + `isolation` inputs. Claude's adapter renders `--permission-mode <mode>` plus the `env -u ...` prefix (`WORKER_ENV_UNSET` + `HOST_ONLY_ENV_UNSET` on host isolation, CAM-242); codex's adapter renders codex's own sandbox/approval flags and env vars from the same two inputs. The `--permission-mode` cam-CLI-flag ban (curated invariant, `test/no-permission-mode-flag.test.ts`) is unaffected: `permissionMode` stays an internal supervisor-to-adapter input, never a CLI flag on any cam subcommand, for both backends.

Mismatch **(d) agent-prompt injection** is a METHOD-shaped concern for the same reason: claude's adapter renders `--agent <agentName>` against `.claude/agents/<name>.md` frontmatter (the agent body IS the system prompt, ADR-0020); codex has no `--agent` analog. The spike's direction: codex's adapter is responsible for injecting the equivalent agent body (`.claude/agents/<name>.md` content) via whatever mechanism codex's CLI exposes for a system/developer-role prompt (a `-i`/instructions-file flag or an inlined prefix in the task prompt): this is internal to codex's `buildSpawnArgv`, not a new caller-visible method, and not implemented in this slice (no codex dispatch code lands here). Whether codex needs its own `.claude/agents/`-equivalent prompt files, or can reuse the existing markdown bodies verbatim, is left to the follow-up implementation issue.

### The shared contract: completion detection stays outside the adapter

Mismatch **(c) completion-detection** resolves as a **SHARED CONTRACT**, not an adapter method. The report/sentinel/JSON boundary (`CAM_*_STATUS` sentinel lines tailed from `capture-pane`, `<review>` tags, `worker-report.json` / `review-report.json` parsed through the shared hand-rolled guard, `report-parse.ts`, ADR-0038) is already backend-agnostic: it is text and JSON on disk/pane, produced by whatever process the supervisor spawned, with zero backend-specific parsing logic on the read side today. The supervisor's poll loop (`loop.ts`) does not need to know which backend produced the pane output or the report file. This is deliberately kept OUTSIDE `BackendAdapter`: an adapter method here would tempt backend-specific parsing to leak into the shared poll loop, which is the one piece of the pipeline that must stay identical across backends for a MIXED run (e.g. `implementer=codex, reviewer=claude`) to interoperate. The adapter's only obligation toward this contract is indirect, via mismatch (d): whatever backend is spawned must be prompted (through its agent-prompt injection) to emit the identical `CAM_*_STATUS` / `<review>` / report-JSON shapes claude emits today.

This is the enabler of future mixed-backend runs: because completion detection is a fixed shared contract rather than a per-backend method, adding codex does not require the supervisor to branch on backend anywhere in the poll/parse path, only at the single dispatch point where `buildSpawnArgv` is called for a given actor's resolved backend.

### Codex-specific concerns: direction only, no implementation

Two codex-specific concerns are OUT of this slice's implementation but need a recorded direction so the eventual codex-adapter issue has a starting point:

- **Env/sandbox model (part of mismatch e).** Codex has its own sandbox/approval model and its own nesting/auth env vars, distinct from claude's `CLAUDE*` env-strip list (`WORKER_ENV_UNSET`, `HOST_ONLY_ENV_UNSET`). Direction: codex's adapter renders an independent env-strip/sandbox-flag list from the same `permissionMode`/`isolation` inputs; it does not attempt to reuse claude's literal var names. The concrete codex env var list is deferred to the implementation issue (requires inspecting the real `codex` CLI, out of scope for a zero-LLM spike).
- **Claude-transcript-coupled token-ceiling backstop (`loop.ts:1189`, reading `readWorkerTokens` -> `src/transcript/usage.ts`).** This is the RISKIEST sub-area per the CAM-54 spec: the per-worker token ceiling and the orchestrator-side context-budget/recycle backstop (`orch-budget.ts`, `orch-recycle-watch.ts`) are hard-coupled to claude's `.jsonl` transcript shape and the `--session-id` lowercase-uuid resume dance (`run.ts` orchestrator wrapper, `run.ts:281-285`). Codex's session/transcript model is unknown at spike time. Direction recorded here (not implemented): either (1) codex exposes an equivalent transcript/usage artifact that a codex-specific `readWorkerTokens` variant can parse into the same `TokensEventDetail` shape, keeping the ceiling enforced, OR (2) codex workers run with **documented graceful degradation**: the per-worker token ceiling and the orchestrator recycle backstop are silently inapplicable (never silently BROKEN: the supervisor must log, not crash or mis-detect, when `readWorkerTokens` cannot resolve a codex session) until a codex transcript equivalent is confirmed to exist. This decision, not an implementation, is deferred to the codex-adapter follow-up issue; most of the recycle-backstop surface lives in the orchestrator-persona path, itself out of this slice's scope (see below), but a codex worker's completion/token-read path is in scope for that follow-up because worker actors are in scope here.

### Scope

This slice covers the four worker actors (implementer, planner, auditor, reviewer) only, the same scope ADR-0046 already fixed. Explicitly deferred to follow-up issues, unchanged from ADR-0046: orchestrator-persona (`run.ts`, the `buildOrchestratorPaneCommand` bounded-respawn wrapper, `run.ts:267`-area `claude --agent subagent-orchestrator` invocation), the retry launcher (`retry/launcher.ts`), and auth-preflight codex parity (`run-auth-preflight.ts`). `cam ship` stays deterministic and zero-LLM (ADR-0009, `ship-runner.ts:36`) and needs no adapter at all. No codex dispatch code, no codex CLI argv, and no `.claude/agents/` codex variant lands in this story; this ADR is the design record only.

## Consequences

`BackendAdapter` becomes a one-method-per-actor-class seam (`buildSpawnArgv(actor, opts)`) instead of four near-duplicated builder functions, which the follow-up implementation issue will consolidate `worker-argv.ts` / `plan-argv.ts` / `review.ts` behind with no behavior change to the existing claude path (their current pure-function, single-quote-escaping, `workerEnvPrefix`-sharing design carries over unchanged as the claude adapter's implementation). `readBackend` becomes a per-phase accessor mirroring `readPhaseModel`, which is a small, mechanical, additive change (existing single-key callers keep working via a default phase or a compatibility wrapper, to be decided by the implementation issue). Completion detection, having been fixed as a shared contract rather than an adapter method, means the supervisor poll loop in `loop.ts` needs zero backend-awareness to support a mixed run; the cost of this decision is pushed entirely onto agent-prompt injection (mismatch d): every backend's adapter must reliably get its agent to emit the identical sentinel/report shapes, or mixed runs silently fail completion detection with no adapter-level fallback. The token-ceiling/recycle backstop is left as an explicit open risk: until the codex-adapter follow-up resolves it (transcript equivalent or graceful degradation), codex workers must not be assumed to have a working per-worker token ceiling, and the supervisor must not crash or silently ignore this gap when it eventually spawns a codex worker.
