- [resolved 2026-06] **ink-testing-library keypress simulation** (US-003, 2026-06-14): `const { stdin } = render(...)` exposes a fake Stdin whose `stdin.write('n')` emits a 'data' event synchronously, which Ink's useInput hook processes immediately. Use this to assert that injected runTmux/dispatch callbacks receive the correct args (e.g. `['send-keys', '-t', orchPane, '/cam-next', 'Enter']`). The old menu.test.ts comment "cannot easily simulate keypresses without stdin access" was wrong; stdin is returned by render() in ink-testing-library.

- [resolved 2026-06] **tmux window-resized hook + resize-pane -x clamp** (CAM-48, US-002, 2026-06-14): `resize-pane -x` rejects tmux format expressions like `#{window_width}` with "width invalid" - the value must be a pre-computed literal integer. tmux comparison modifiers (`#{>:a,b}`) are lexical (string), not numeric, so a numeric min/max clamp cannot be expressed in pure tmux format. Solution: use `run-shell 'w=#{window_width}; t=$(( (w*26+50)/100 )); t=$(( t<34?34:t>80?80:t )); tmux -L <socket> resize-pane -t <paneId> -x $t || true'`. `run-shell` causes tmux to expand `#{window_width}` to a numeric literal before passing the string to `sh -c`, enabling shell `$(())` arithmetic for the clamp. Use `(w*26+50)/100` (round-half-up) not `w*26/100` (truncation) to match `Math.round` in the JS helper. Bounds 34-80, proportion 26%: at 188 cols the column is 49 cols, wide enough for the tokens status row. Interpolate the socket constant (CAM_TMUX_SOCKET) in the TS template string instead of a hardcoded literal. Verified: w=100->34, w=188->49, w=220->57, w=400->80.

- [resolved 2026-06] **ink-testing-library setState re-render timing** (US-005, 2026-06-14): `useState` updates triggered inside `useInput` handlers are async in React 19. `stdin.write('j')` fires the handler synchronously but the re-render (and the updated `lastFrame()`) happens as a scheduled macrotask. Tests that assert `lastFrame()` after state-changing keypresses need `await new Promise(r => setTimeout(r, 0))` (one macrotask tick) to let React flush. Tests that only assert synchronous side-effects (like injected `runTmux` calls) do not need the tick.

- [resolved 2026-06] **chalk.level and ANSI in ink-testing-library** (US-005, 2026-06-14): ink-testing-library's custom `Stdout` class has no `isTTY` flag, so chalk auto-detects color level 0 (no colors) when the test runner is not a TTY. To assert raw ANSI escape codes from `lastFrame()`, call `chalk.level = 3` in `beforeAll` and restore in `afterAll` (import `ColorSupportLevel` from chalk for the saved-value type). The 24-bit bg escape for `#4EBE7D` is `[48;2;78;190;125m` (the substring after the ESC byte). Arrow-key sequences passed to `stdin.write` must include the full ESC byte: down = `'[B'`, up = `'[A'`.

- [resolved 2026-06] **Ink 7 ESC pending-buffer (US-006, 2026-06-14)**: A lone `\x1b` byte written to ink-testing-library stdin is NOT immediately emitted as a keypress. Ink's `createInputParser` treats `\x1b` alone as a "pending escape" (could be the start of a multi-byte ANSI sequence) and schedules a 20ms flush via `setTimeout`. Tests that write `\x1b` and then assert `key.escape` behavior must wait > 20ms: use `await new Promise((r) => setTimeout(r, 50))` instead of the 0ms `tick()`. The handler-level check `if (key.escape)` is still correct; the delay is only a testing concern. Detection: if `await tick()` (0ms) leaves the escape state unchanged, the pending-escape buffer is the likely cause.

- [resolved 2026-07] **A terminal state-file signal must be written by whichever call site runs LAST in the teardown chain, not by the call site that "logically" decides it (US-001, CAM-191, 2026-07-07, ADR 0013)**: `runSupervisor`'s inner 'complete' branch used to write `phase:shipping` (via `autoShipFn`) before returning; but `finishTerminal` (still inside `runSupervisor`) then runs `onProgress`'s unlink-on-complete, and after `runSupervisor` returns, the OUTER `runSidecarLoop` calls `clearActive()`, which implicitly rewrites the state file as `phase:idle` (no explicit `setPhase('idle')` call exists anywhere -- `makeClearActive` just omits `phase` and passes `active:false`, and `renderStateFile` derives `effectivePhase: 'idle'` from that). Any state-file write from an inner call site is clobbered by outer teardown that runs afterward, even when the inner write is logically "the decision." Fix pattern: move the whole gated decision (here: `result.status==='complete' && lastVerdict==='CLEAN' && marker-absent`) to the LAST point in the call chain, using data threaded back from the inner call (`SupervisorResult.status`) plus the SAME `readPrd`/`writePrd`/`clock` triple already returned by `buildOpts()` (no need to invent a new prd-access seam on the outer options type -- the inner options bag already has it, just read it again after the inner call returns). The prd-marker write (an idempotent fire-once dedup, ADR 0008) stays correct because it is data, not a file the teardown chain touches; only the STATE-FILE phase write needed to move. General rule: before adding a new state-file write inside any function, trace every teardown/reset call that runs between that write and the point where the NEXT reader will look at the file; if any of them touches the same file unconditionally, the write must move past the last one, even if that means splitting a "single" decision across two nesting levels (RunSupervisorOptions vs RunSidecarLoopOptions here).

- **`renderStateFile` is read-modify-write over `phase`, gated by an opt-in `cwd` field; `makeClearActive` no longer collapses `phase` to `idle` (US-001, CAM-195, 2026-07-11, Defect 3 root fix)**: the CAM-191 ordering workaround (previous bullet, now `[resolved 2026-07]`) treated the SYMPTOM (clobber ordering) rather than the ROOT CAUSE: `makeClearActive` called `renderStateFile` with `active:false` and no `phase`, and the old derivation (`input.phase ?? (input.active !== false ? 'implementing' : 'idle')`) always collapsed an absent `phase` to `idle` whenever `active` was `false` — regardless of what phase was actually on disk. Fixed by adding an optional `cwd` input field to `renderStateFile`: when `phase` is absent AND `cwd` is given, it reads the CURRENT on-disk phase at `cwd` (via a `readCurrentPhase` helper reusing `parseStateFile`) and preserves it; a nonexistent/unparseable/phase-less file still defaults to `idle`. `cwd` is opt-in specifically so every OTHER pre-existing caller that omits both `phase` and `cwd` (e.g. `runNext`'s two branches, `makeOnProgress` in `host.ts`) keeps its exact legacy `active`-derived behavior unchanged — only `makeClearActive` (the file the defect traced to) was updated to pass `cwd`. Consequence: the CAM-191 reorder (auto-ship positioned AFTER `clearActive` specifically to survive its implicit idle-rewrite) is no longer needed and was retired — auto-ship now runs in its natural position BEFORE `clearActive` in `runSidecarLoop`, and `test/supervisor/auto-ship-real-writers.test.ts` (unmodified) still proves phase:shipping survives the teardown chain, now because `clearActive` is phase-preserving rather than because of ordering. General rule: a boolean flag (`active`) should never be the source of truth for a richer enum (`phase`) that a SEPARATE writer might have already set to something else; prefer read-modify-write over the enum field itself, gated opt-in so legacy callers are unaffected.

- **`[resolved 2026-07]` A vendored "byte-for-byte verbatim" file CAN carry a deliberate local divergence, documented not silently patched (US-R1-001, CAM-286, 2026-07-12)**: closed the latent regression the US-002 bullet above flagged (`vendor/check-agent-frontmatter.ts`'s `REQUIRED_TOP_LEVEL_KEYS` still required `model` after US-002 stripped `model:` from all 5 persona files). Rather than treat "vendored verbatim from upstream `reporter`" (`vendor/README.md`) as an absolute constraint, dropped `'model'` from `REQUIRED_TOP_LEVEL_KEYS` locally (check #6, the shape-validate-when-present rule, is untouched) and documented the divergence in three places so a future re-vendor doesn't silently clobber it: (1) a header comment in `vendor/check-agent-frontmatter.ts` itself pointing at this note, (2) a new "Local divergences from upstream" section in `vendor/README.md` naming the exact patch and the story/tracker id, (3) a locking regression test (`test/vendor/check-agent-frontmatter-standalone.test.ts`, "CAM-286: smoke exits 0 for an agent file with no 'model:' frontmatter key") that would catch a future re-vendor silently re-adding the requirement. General rule: a vendor/README.md "verbatim copy" convention documents *provenance*, not an absolute never-diverge rule -- a real, currently-breaking mismatch between the vendored copy and the consuming repo's own materialized files is exactly the case where a documented, re-vendor-survives-via-comment local patch is the right call over waiting on an upstream fix in a separate repo this PRD has no access to. After any edit to `vendor/*.ts`, `bun run embed-vendor` must be re-run before `embed-vendor:check`/`bun test` will see the fix (the consumed copy is `src/vendor/_generated.ts`, not the on-disk `vendor/` file).
