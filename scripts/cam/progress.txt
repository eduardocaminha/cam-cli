## Codebase Patterns

Durable patterns carried across cycles. Implementers append new ones as they emerge.

- **Bun runtime**: prefer `Bun.spawn` / `Bun.$` / `Bun.file` over `node:child_process` / `node:fs` in NEW code. But match the surrounding file's idiom: `src/commands/run.ts`, `dashboard.ts`, and `status.ts` already use `node:fs` / `node:path` / `node:child_process`; keep that style there, do not mix `Bun.file` mid-file.
- **Permission mode**: never register a `--permission-mode` CLI flag on any subcommand parser, enforced by `test/no-permission-mode-flag.test.ts` (greps `index.ts` and `src/commands/`). The literal may appear only inside a forwarded argv (e.g. the orchestrator `claude --permission-mode bypassPermissions` in `run.ts`, intentional, and the spawned worker argv in CAM-22).
- **noUncheckedIndexedAccess**: tsconfig has it on. Array indexing and regex capture groups are `T | undefined`; guard with `?? fallback` or a justified non-null assertion. JSON.parse results need runtime shape checks before property access.
- **`bun test` green is NOT proof of type-safety**: the runner passes even when `tsc --noEmit` would fail. Always run `bun run typecheck` separately and trust its exit code before claiming the gate passed.
- **Read-only readers never throw**: `readSnapshot` / `buildStatusReport` and their helpers wrap every IO in try/catch and fall through to defaults, because dashboard/status are read-only and a render failure must not brick the operator's terminal (see `readPrd` / `readState` in `dashboard.ts`).
- **Transcript discovery**: Claude Code transcripts live at `~/.claude/projects/<encode(cwd)>/<sessionId>.jsonl`, where `encode = cwd.replace(/[^a-zA-Z0-9]/g, '-')` (verified empirically). Filename == sessionId. Each line is one JSON object; assistant lines carry `message.usage` with `input_tokens` / `output_tokens` / `cache_read_input_tokens` / `cache_creation_input_tokens`. Dedupe by `(message.id, requestId)` before summing (one JSONL line per content block carries identical usage; inflation ~1.44x).
- **src/tmux/session.ts is the canonical session module**: `projectSessionName`, `ensureProjectSession`, `openPaneInSession`, `isInsideProjectSession`, `tmuxArgs` all live here with injectable `SpawnFn`. All tmux calls go through `tmuxArgs(sub)` which prepends `['-L', 'cam']`; test fakes route by `args[2]` (guard: `args[0] === '-L' ? args[2] : args[0]`).
- **tmux worker primitives (CAM-22)**: `respawn-pane -k -t <pane> <cmd>` kills the running command and reuses the SAME pane id; `wait-for <chan>` blocks the client until `wait-for -S <chan>` signals it (the signal is NOT guaranteed buffered if sent before the wait, so always confirm the outcome by reading `prd.json` / `handoff.json`, never trust the channel alone); `capture-pane -p [-S -N]` dumps a pane to stdout for sentinel grepping.
- **Claude worker invocation (CAM-22)**: custom slash commands do NOT run in headless `-p` mode. A worker session is `claude -p --permission-mode <mode> --session-id <uuid> --output-format json --agent <name> "<task>"`, never `claude -p "/cam-..."`. Autonomous workers (implementer/reviewer) exit on their own so a chained `; tmux -L cam wait-for -S <chan>` works; interactive workers (plan, optional review) do NOT exit, so detect completion by scraping `capture-pane -p` for the `CAM_*_STATUS` / `<review>` sentinel.
- **Ink screens**: success/failure is signalled by the glyph (✓ accent / ✗ destructive), never by divider color. Render and look at the real output; do not trust header comments (see `lessons.md` 2026-06-05).
- **Tests**: `bun test` from repo root. Tests for `src/commands/*` and `src/tmux/*` live FLAT at `test/<name>.test.ts` (e.g. `test/next.test.ts`, `test/tmux-session.test.ts`); subdir mirrors exist for `test/retry/*`, `test/transcript/*`, and (new in CAM-22) `test/supervisor/*`. Inject fake reader/writer/spawn shapes (and injectable `home` / `genSessionId`) instead of touching real stdin/stdout/`~/.claude`/tmux.
- **Commits**: conventional commits required (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`).
- **No em dashes** in persisted files (PRD notes, progress, docs): use colon, comma, parentheses, or period.
- **Pure transcript parser pattern**: `parseTranscriptUsage` splits on `\n`, `JSON.parse` each trimmed line in a try/catch, checks `message?.usage` existence, accumulates with `toNumber()` guard (returns 0 for non-number). `formatTokens` uses `>= 1_000_000` / `>= 1_000` thresholds. Module lives in `src/transcript/usage.ts`; tests under `test/transcript/usage.test.ts`. `orchestratorTranscriptPath(cwd, claudeDir)` reads `.claude/.cam-orch-session`; CAM-22 generalizes it to `transcriptPathForSession(uuid, cwd, claudeDir)`.
- **openPaneInSession returns pane id (US-001)**: the function now uses `stdio: 'pipe'` and `-P -F #{pane_id}` to capture and return the stable pane id string (e.g. `%5`). All test fakes for split-window must handle `opts?.stdio === 'pipe'` and return a non-empty `stdout` buffer, or they will crash with `Cannot read property toString of undefined`.
- **Worker pane marker (US-001)**: the first write of `.claude/.cam-worker-pane` happens in `plan.ts` immediately after `openPaneInSession`. Supervisor and lifecycle commands address the slot via `readWorkerPaneMarker(claudeDir)`. Returns null if the file is missing or empty; never throws.
- **Supervisor timeout pattern (US-011)**: `tmux wait-for` has NO native timeout. Bound it by running via `spawnSync(..., { timeout: ms })`; when the deadline fires, spawnSync kills the client process (SIGTERM) and sets `result.signal`. Check `result.signal !== null` for `timedOut`. Pane-death detection: `spawnSync('tmux', ['-L', 'cam', 'list-panes', '-t', paneId])` exits 0 if pane exists, non-zero if dead. Timeout/pane-died blocked outcomes continue the loop (proceed to decideNextAction) rather than exiting, enabling recovery to the next story. Decouple reviewer wait (`ReviewWaitForFn = (channel) => void`) from supervisor `WaitForFn` to avoid forcing the timeout signature onto the unbounded review wait.
- **Sentinel polling mode (US-012)**: interactive workers (plan/review with human input) do NOT exit on their own, so the supervisor polls `capture-pane` instead of waiting for a tmux channel. Use `implementerMode: 'sentinel'` in `RunSupervisorOptions`; inject `sleepFn` (no-op for tests), `nowMs` (deterministic time source), and `pollIntervalMs`. `buildImplementerWorkerArgv({ interactive: true })` omits `-p` and `--output-format` and the wait-for chain. `parseAnySentinel(text)` in `result.ts` detects `CAM_IMPLEMENTER_STATUS=*`, `CAM_REVIEWER_STATUS=*`, or `<review>...</review>` tags. Same timeout/pane-died semantics as the exit path: both `continue` the supervisor loop.
- **Structured worker events (US-013)**: `src/supervisor/events.ts` defines `WorkerEvent { ts, storyId, uuid, kind, detail }` and the supervisor appends one JSON line per lifecycle step to `.claude/cam-worker-events.jsonl`. The logger is injected (`logEvent?: WorkerEventLogger`); default `makeFileEventLogger(path)`, tests use `makeInMemoryEventLogger()`. Both injections (`logEvent`, `readWorkerTokens`) are OPTIONAL: absent `logEvent` means zero events and zero behavior change (existing loop tests pass untouched). Emit sites in `loop.ts`: `worker-start` right after `respawn-pane`, `worker-end` after `waitFor`/poll-loop, `result`+`tokens` only where `readWorkerOutcome` produced a real outcome (NOT on timeout/pane-death: no canonical per-story record exists there). `buildResultDetail(outcome, handoff)` builds the rich `result` detail: `filesChanged` = handoff `createdFiles ++ modifiedFiles`, `gates` = `pass` only for a `pass` outcome else `unknown` (supervisor has no per-worker gate transcript), `docsValidated` mirrors handoff `officialDocsValidated`. The `tokens` event reuses `readWorkerTokens(uuid, cwd, claudeDir)` -> `transcriptPathForSession` + `parseTranscriptUsage`, skipped (no event) when the transcript is absent, never logs zeros. Logger uses synchronous `appendFileSync` (not async `Bun.file`) to match the supervisor's all-synchronous injected I/O.
- **Per-story tokens in dashboard (US-014)**: `readSnapshot` now returns `storyTokens: Record<storyId, TranscriptUsage>`. It reads each story's `.claude/.cam-worker-<id>.session` marker (project `.claude`, via `readWorkerSessionMarker`), resolves the transcript with `transcriptPathForSession(uuid, cwd, claudeDir)`, and sums usage. `readTranscriptTokens` was generalized to take a resolved path (one reader for the orchestrator transcript AND per-story transcripts); the orchestrator caller now resolves the path first. Stories with no marker (or unreadable transcript) are omitted from the map, so `Dashboard.tsx` `StoryRow` shows a muted `STORY_TOKENS_PLACEHOLDER` (`·`) instead of crashing; stories with data show `renderTokensLine(...)` next to the row. State stays signalled by the glyph (✓/→/◌), never the divider. The Ink render is asserted via `ink-testing-library` (`test/dashboard.test.ts`), not a comment.
- **Single-supervisor lock (US-015)**: `src/supervisor/lock.ts` is the pure guard: `acquireSupervisorLock(pid, project, io)` over an injected `LockIo` (`read`/`write`/`remove`/`pidAlive`/`clock` + optional `logEvent`). It refuses when an existing lock names a DIFFERENT, live pid; takes over a dead pid after emitting a `stale-lock` event (the union in `events.ts` gained `'stale-lock'`, a supervisor-level event with `uuid: 'supervisor'`); overwrites an unparseable lock with no event. Wired in `next.ts` (NOT in the pure `runSupervisor`, which stays side-effect-free): acquire right after the worker-pane check and before the state-file write, reject with exit 1 on conflict, and release at every terminal return AND via a single process-wide SIGINT/SIGTERM handler (`installShutdownHandler`, module-singleton tracking `currentLockRelease`). `acquireLock` and `onShutdown` are injectable on `NextOptions` so tests drive the conflict/release paths without real processes or signals. PID liveness reuses `isPidAlive` from `resume.ts` (do NOT duplicate the signal-0 probe). Lock file `.claude/.cam-supervisor.lock` is gitignored.
- **Rate-limit pause/resume (US-016)**: handled ONLY in the exit-mode worker path of `loop.ts`, gated behind an optional `rateLimitResume?` injection (absent ⇒ zero behavior change; a RATE_LIMIT pane then flows through `readWorkerOutcome` as `unknown` -> blocked exactly as before). After capturing pane text, `detectRateLimit(text)` = the `CAM_IMPLEMENTER_STATUS=RATE_LIMIT` sentinel OR `isRateLimited(text)` (reused from `src/retry/patterns.ts`). On detection the supervisor emits a `'rate-limited'` event (`phase: 'pause'`), awaits `rateLimitResume({ message, attempt })`, emits `phase: 'resume'`, then RESPAWNS the SAME `shellCmd` (same uuid == `--session-id`, same channel marker -> session continuity, AC4), re-waits, and re-captures, bounded by `maxRateLimitRetries` (default 5). A resume-wait timeout reuses the normal timeout path via a labeled `continue outer`; exhausting retries returns blocked `rate-limit retries exhausted`. `result.ts` / `WorkerOutcomeKind` were NOT changed (avoids regressing the sentinel-mode path). The production `rateLimitResume` (in `next.ts`) reuses `parseResetTime` + `calculateWaitMs` from `src/retry/time-parser.ts` and `Bun.sleepSync`, capped at `RL_MAX_SLEEP_MS` (6h). The outer supervisor `while` is now labeled `outer:` so the inner resume loop can bail to the next iteration on timeout.
- **Operator stories do NOT block review (decide.ts, revised 2026-06-09)**: `decideNextAction` runs the review cycle BEFORE gating on `requires:operator` stories. Order: (1) any non-operator `passes:false` -> implement; (2) all non-operator pass AND review not terminal -> review; (3) review terminal AND an operator story still `passes:false` -> `await-operator` (carries `pendingStoryIds`); (4) all pass incl. operator AND review terminal -> complete. `await-operator` maps to `SupervisorStatus 'awaiting-operator'` in `loop.ts` and exits 0 in `next.ts` (success: autonomous work done + reviewed clean, operator ceremony pending), it is NOT a block. `blocked-no-implementable` is now only the degenerate guard (implementable story with no id). This SUPERSEDES the US-005 note (further down this log) that said operator-pending stories block the loop. Rationale: an operator E2E ceremony validates the product; review can change the code, so review must run first. See lessons.md 2026-06-09.
- **Recovery runbook (US-017)**: `docs/recovery-runbook.md` is the canonical operator playbook for a stuck loop. Covers stuck supervisor (find `pid:` in `.claude/cam-loop.local.md`, `cam stop` then `cam resume`), orphaned worker pane (`cam stop`/`cam resume`, or `tmux -L cam respawn-pane -k -t <pane>`), partial story (handoff names it but `prd.json` not flipped: re-run gates, flip `passes:true`, commit), stale `.cam-supervisor.lock` (auto-taken-over on next `cam next`; `rm` only when the recorded pid is dead), and reading `.claude/cam-worker-events.jsonl` to diagnose. Reference facts captured while writing it: `cam stop` SIGTERMs the supervisor pid from the state file + removes the state file + kills the project tmux session (it does NOT remove the lock); `cam resume` is the 4-mode recovery (continue/respawn/prompt/noop + explicit `--mode reset-*`). Keep the runbook's file table in sync if the `.claude/` runtime filenames change.
- **ensurePushed hook (US-001)**: optional `ensurePushed?: () => { ok, pushed, sha, detail }` on `RunSupervisorOptions`. Called INSIDE the `if (outcome.kind === 'pass' ...)` block, after `writeSessionMarker` and before falling through to `continue`. Both exit-mode and sentinel-mode pass branches share the identical call site pattern. Absent hook: zero behavior change (existing tests pass unmodified). `ok:false` returns `{ status: 'blocked', ... }` immediately; `ok:true` is a no-op (loop continues). Production adapter in `next.ts` uses `spawnSync` with `stdio:'pipe', encoding:'utf8'` for `git push origin <branch>` (treats "Everything up-to-date" as `pushed:false ok:true`) then cross-checks `git rev-parse HEAD` vs `git rev-parse origin/<branch>`. Captures stderr separately (supervisorSpawn drops stderr; use spawnSync directly in the adapter).
- **'pushed' event (US-002)**: the supervisor emits one `'pushed'` `WorkerEvent` per push verification, RIGHT after `ensurePushed()` returns and BEFORE the `ok:false` blocked return, so a failed verification still leaves an auditable record. Detail is `PushEventDetail { sha, pushed, ok, detail }` (exported from `events.ts`; added to the `WorkerEventDetail` union for grep even though `Record<string,unknown>` already structurally accepts it). Reuses the existing guarded `emit()` helper (no-op when `logEvent` absent), so absent-logger and absent-`ensurePushed` both emit zero events. Story id is the ACTUAL completed story (`outcome.storyId` / `sentinelOutcome.storyId`), never `advisoryStoryId`. Doc Maintenance: the kind list in `docs/recovery-runbook.md` (table row + grep examples) and `CHANGELOG.md [Unreleased]` were updated in the same change.
