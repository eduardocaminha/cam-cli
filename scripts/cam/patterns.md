# Codebase Patterns

Durable, never-truncated home for reusable project conventions (the old
top-of-progress.txt block, CAM-31). This file is versioned on main and read by
agents to absorb project conventions without re-reading the whole codebase. Add
a bullet whenever a story reveals a reusable insight (a convention, a library
quirk, a gotcha). Unlike the per-story factual record (the event log) and the
per-story handoff (handoff.json), this knowledge persists.

- **Bun runtime**: always `Bun.spawn` / `Bun.$` / `Bun.file` over `node:child_process` / `node:fs`.
- **Permission mode**: never register a `--permission-mode` CLI flag on any subcommand (enforced by `test/no-permission-mode-flag.test.ts`). It is forwarded only to the spawned `claude` process.
- **claude -p is forbidden** (subscription rule, CAM-42): workers are interactive TUI `claude` sessions detected by polling `capture-pane` for the sentinel; never reintroduce `-p` in a worker argv (tests assert its absence). `claude -p` survives only in the separate `cam claude` retry wrapper.
- **noUncheckedIndexedAccess**: array indexing and regex capture groups are `T | undefined`. Guard with `?? fallback` or a justified non-null assertion.
- **Ink screens**: success/failure is signalled by the glyph (check accent / cross destructive), never by divider color. Render and look at the real output; do not trust header comments (see `lessons.md` 2026-06-05).
- **Tests**: `bun test` from repo root; test files live under `test/`, mirroring source. Inject fake reader/writer shapes instead of touching real stdin/stdout.
- **Commits**: conventional commits required (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`).
- **No em-dash in persisted .md** (project rule, 2026-05-20): use colon, comma, parens, period, or cut the connector.
- **issues.local.json hygiene** (CAM-47 dogfood, 2026-06-14): `cam issue` / `/cam-issue create` allocate the next id from the top-level `next_id` field and then bump it. If you hand-edit issues with explicit ids (bulk-filing), advance `next_id` to `max(id)+1` in the same edit, or the next automatic allocation collides with an existing id (a duplicate `CAM-N` appears, one closed and one open). A live `cam run` orchestrator is a concurrent writer of this file (via `/cam-issue`): do not hand-edit issues.local.json while a session is running on the same working tree.
- **ink-testing-library keypress simulation** (US-003, 2026-06-14): `const { stdin } = render(...)` exposes a fake Stdin whose `stdin.write('n')` emits a 'data' event synchronously, which Ink's useInput hook processes immediately. Use this to assert that injected runTmux/dispatch callbacks receive the correct args (e.g. `['send-keys', '-t', orchPane, '/cam-next', 'Enter']`). The old menu.test.ts comment "cannot easily simulate keypresses without stdin access" was wrong; stdin is returned by render() in ink-testing-library.
- **tmux window-resized hook + resize-pane -x clamp** (CAM-48, US-002, 2026-06-14): `resize-pane -x` rejects tmux format expressions like `#{window_width}` with "width invalid" - the value must be a pre-computed literal integer. tmux comparison modifiers (`#{>:a,b}`) are lexical (string), not numeric, so a numeric min/max clamp cannot be expressed in pure tmux format. Solution: use `run-shell 'w=#{window_width}; t=$(( (w*26+50)/100 )); t=$(( t<34?34:t>80?80:t )); tmux -L <socket> resize-pane -t <paneId> -x $t || true'`. `run-shell` causes tmux to expand `#{window_width}` to a numeric literal before passing the string to `sh -c`, enabling shell `$(())` arithmetic for the clamp. Use `(w*26+50)/100` (round-half-up) not `w*26/100` (truncation) to match `Math.round` in the JS helper. Bounds 34-80, proportion 26%: at 188 cols the column is 49 cols, wide enough for the tokens status row. Interpolate the socket constant (CAM_TMUX_SOCKET) in the TS template string instead of a hardcoded literal. Verified: w=100->34, w=188->49, w=220->57, w=400->80.
- **ink-testing-library setState re-render timing** (US-005, 2026-06-14): `useState` updates triggered inside `useInput` handlers are async in React 19. `stdin.write('j')` fires the handler synchronously but the re-render (and the updated `lastFrame()`) happens as a scheduled macrotask. Tests that assert `lastFrame()` after state-changing keypresses need `await new Promise(r => setTimeout(r, 0))` (one macrotask tick) to let React flush. Tests that only assert synchronous side-effects (like injected `runTmux` calls) do not need the tick.
- **chalk.level and ANSI in ink-testing-library** (US-005, 2026-06-14): ink-testing-library's custom `Stdout` class has no `isTTY` flag, so chalk auto-detects color level 0 (no colors) when the test runner is not a TTY. To assert raw ANSI escape codes from `lastFrame()`, call `chalk.level = 3` in `beforeAll` and restore in `afterAll` (import `ColorSupportLevel` from chalk for the saved-value type). The 24-bit bg escape for `#4EBE7D` is `[48;2;78;190;125m` (the substring after the ESC byte). Arrow-key sequences passed to `stdin.write` must include the full ESC byte: down = `'[B'`, up = `'[A'`.
- **Ink 7 ESC pending-buffer (US-006, 2026-06-14)**: A lone `\x1b` byte written to ink-testing-library stdin is NOT immediately emitted as a keypress. Ink's `createInputParser` treats `\x1b` alone as a "pending escape" (could be the start of a multi-byte ANSI sequence) and schedules a 20ms flush via `setTimeout`. Tests that write `\x1b` and then assert `key.escape` behavior must wait > 20ms: use `await new Promise((r) => setTimeout(r, 50))` instead of the 0ms `tick()`. The handler-level check `if (key.escape)` is still correct; the delay is only a testing concern. Detection: if `await tick()` (0ms) leaves the escape state unchanged, the pending-escape buffer is the likely cause.
- **Test timeout with no-op sleepFn**: when injecting `sleepFn: () => {}` in tests for `waitForOrchestrator`, always pair it with a tiny `waitTimeoutMs` (5-10ms). The `while (Date.now() < deadline)` loop spins the CPU until the deadline expires; with a 5_000ms budget and a no-op sleep the test actually burns 5 real seconds and Bun's 5s per-test timeout kills it. Correct: `sleepFn: () => {}, waitTimeoutMs: 5`. (US-006, 2026-06-15.)
- **Single-hub dispatch invariant (CAM-55)**: `cam run` is the only dispatch hub. CLI subcommands (`cam plan`, `cam issue`, `cam next`, `cam ship`) are thin-proxies: detect the orchestrator session and inject the request via atomic `send-keys` (text + Enter in one call); if no session exists, bootstrap `cam run --no-attach` first and wait for the `.claude/.cam-orch-ready` marker before injecting. Workers run in a single reused titled 3rd pane (mutex: dispatch only when session has exactly 2 panes). Completion is push-report (worker writes a result file at exit), not pull-based scrollback polling. The idle-guarantee (ensuring the orchestrator is idle before the worker pushes its report) is its own story (US-008), not folded into the proxy.
- **@cam_label pane-labeling pattern (US-002, 2026-06-15)**: Label any pane before dispatch with `tmux set-option -p -t <paneId> @cam_label <value>`. The session-level `pane-border-format #{@cam_label}` (set in run.ts `setupPanes`) picks this up automatically for any pane added to the session later, including the worker pane. `set-option -p` is validated by tmux docs: pane-scoped `@`-prefixed user options are supported. In the supervisor (loop.ts), the label is set immediately before `respawn-pane -k`; in the review branch, before `reviewDispatch`. The label is best-effort (silent no-op if the pane is not yet open).
- **Mutex busy check in dispatch sites (US-009, 2026-06-15)**: Every thin-proxy dispatch site (plan, next, issue, review, ship) must call `paneCountMutex(sessionName, tmuxSpawnFn)` after the alive/bootstrap path and before `sendKeysWhenIdle`. If the result is `'busy'`, the command calls `printError('worker busy', 'blocked until the worker-pane closes')` and returns exit code 1 without sending any keys. Test helpers that fake `tmuxSpawnFn` must handle ALL `list-panes` format strings: `#{pane_index}\t#{pane_current_command}` (orchestratorAlive), `#{pane_index}\t#{pane_id}` (getOrchPaneId), and `#{pane_id}` (paneCountMutex). If `#{pane_id}` is missing from the fake, `paneCountMutex` gets empty output, counts 0 panes, and returns `'busy'`, breaking the happy-path test. Use `paneMutexBusy` option in `makeFakeTmuxSpawn` to return 3 pane IDs (busy) vs 2 (available).
- **Idle-guarantee before send-keys (US-008, 2026-06-15)**: All thin-proxy commands (plan, next, issue, review, ship) must call `sendKeysWhenIdle` (src/tmux/dispatch.ts) instead of bare `tmuxSpawnFn send-keys`. `sendKeysWhenIdle` polls `capture-pane -p -t <paneId>` until `isOrchPaneIdle` returns true (no spinner glyph ⠋-⠏, no active tool-call glyph ◆ in the last 5 lines, and at least one line ending with `>` or `❯`). Fallback on timeout: log to stderr + still send (never block indefinitely). Default `idleTimeoutMs` is 5 000 ms; tests must inject `capturePaneFn: () => '> '` so the idle check passes immediately without a real tmux call. All test fake spawn fns (makeFakeTmuxSpawn) must handle `capture-pane` subcommand by returning idle content, or the idle-loop will spin for 5 s and hit Bun's per-test timeout.
- **Sidecar-supervisor invariant (US-FIX-001, 2026-06-15)**: the deterministic loop is a SIDECAR, not in-process and not absorbed by the LLM. Roles: `cam run` = sidecar host (spawns `runSupervisor` as a detached background process); the sidecar = the deterministic loop driver (gated on the `active` flag in `.claude/cam-loop.local.md`; holds the supervisor lock; carries the CAM-36 no-progress streak, CAM-44 dead-worker backoff, MAX_ITERATIONS, event log); the LLM orchestrator = human interface (narrates the sidecar's terminal report and routes plan/review/ship/issue), NOT the loop driver; `cam next` = trigger (a thin-proxy that flips `active:true`, never calls `runSupervisor` in-process); `scripts/cam/worker-report.json` = push completion signal (the worker writes it on exit; the sidecar reads it, no scrollback poll). The "orchestrator absorbs the loop" model is REJECTED: an LLM-driven loop loses every deterministic guard above.
- **Report-file completion detection (US-004, 2026-06-15)**: The supervisor poll loop uses an optional injected `ReadWorkerReport` dependency to detect worker completion instead of polling `capturePane + parseAnySentinel`. When `readWorkerReport` is injected and returns a non-null `WorkerReport`, the loop exits with `pollOutcome='sentinel'`. The state-primary outcome is still confirmed via `readWorkerOutcome` (prd.json + handoff.json). The fallback to `capturePane + parseAnySentinel` is preserved for backward compat when `readWorkerReport` is absent. `clearWorkerReport` should be called before `respawn-pane -k` to erase any stale report from the previous run (prevents false-positive on first poll tick). In next.ts, `readWorkerReport` reads `scripts/cam/worker-report.json` via `readFileSync`; `clearWorkerReport` uses `existsSync` + `unlinkSync` wrapped in try-catch (node:fs docs: `unlinkSync` throws ENOENT on missing file, `existsSync` returns false gracefully).
