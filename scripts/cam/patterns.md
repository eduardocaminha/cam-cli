# Codebase Patterns

Durable, never-truncated home for reusable project conventions (the old
top-of-progress.txt block, CAM-31). This file is versioned on main and read by
agents to absorb project conventions without re-reading the whole codebase. Add
a bullet whenever a story reveals a reusable insight (a convention, a library
quirk, a gotcha). Unlike the per-story factual record (the event log) and the
per-story handoff (handoff.json), this knowledge persists.

- **Bun runtime**: always `Bun.spawn` / `Bun.$` / `Bun.file` over `node:child_process` / `node:fs`.
- **Permission mode**: never register a `--permission-mode` CLI flag on any subcommand (enforced by `test/no-permission-mode-flag.test.ts`). It is forwarded only to the spawned `claude` process.
- **claude -p is forbidden** (subscription rule, CAM-42): workers are interactive TUI `claude` sessions detected by polling `capture-pane` for the sentinel; never reintroduce `-p` in a worker argv (tests assert its absence). `claude -p` survives only in the separate `cam claude` retry wrapper.
- **noUncheckedIndexedAccess**: array indexing and regex capture groups are `T | undefined`. Guard with `?? fallback` or a justified non-null assertion.
- **Ink screens**: success/failure is signalled by the glyph (check accent / cross destructive), never by divider color. Render and look at the real output; do not trust header comments (see `lessons.md` 2026-06-05).
- **Tests**: `bun test` from repo root; test files live under `test/`, mirroring source. Inject fake reader/writer shapes instead of touching real stdin/stdout.
- **Commits**: conventional commits required (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`).
- **No em-dash in persisted .md** (project rule, 2026-05-20): use colon, comma, parens, period, or cut the connector.
- **issues.local.json hygiene** (CAM-47 dogfood, 2026-06-14): `cam issue` / `/cam-issue create` allocate the next id from the top-level `next_id` field and then bump it. If you hand-edit issues with explicit ids (bulk-filing), advance `next_id` to `max(id)+1` in the same edit, or the next automatic allocation collides with an existing id (a duplicate `CAM-N` appears, one closed and one open). A live `cam run` orchestrator is a concurrent writer of this file (via `/cam-issue`): do not hand-edit issues.local.json while a session is running on the same working tree.
- **ink-testing-library keypress simulation** (US-003, 2026-06-14): `const { stdin } = render(...)` exposes a fake Stdin whose `stdin.write('n')` emits a 'data' event synchronously, which Ink's useInput hook processes immediately. Use this to assert that injected runTmux/dispatch callbacks receive the correct args (e.g. `['send-keys', '-t', orchPane, '/cam-next', 'Enter']`). The old menu.test.ts comment "cannot easily simulate keypresses without stdin access" was wrong; stdin is returned by render() in ink-testing-library.
- **tmux window-resized hook + resize-pane -x clamp** (CAM-48, US-002, 2026-06-14): `resize-pane -x` rejects tmux format expressions like `#{window_width}` with "width invalid" - the value must be a pre-computed literal integer. tmux comparison modifiers (`#{>:a,b}`) are lexical (string), not numeric, so a numeric min/max clamp cannot be expressed in pure tmux format. Solution: use `run-shell 'w=#{window_width}; t=$(( (w*26+50)/100 )); t=$(( t<34?34:t>80?80:t )); tmux -L <socket> resize-pane -t <paneId> -x $t || true'`. `run-shell` causes tmux to expand `#{window_width}` to a numeric literal before passing the string to `sh -c`, enabling shell `$(())` arithmetic for the clamp. Use `(w*26+50)/100` (round-half-up) not `w*26/100` (truncation) to match `Math.round` in the JS helper. Bounds 34-80, proportion 26%: at 188 cols the column is 49 cols, wide enough for the tokens status row. Interpolate the socket constant (CAM_TMUX_SOCKET) in the TS template string instead of a hardcoded literal. Verified: w=100->34, w=188->49, w=220->57, w=400->80.
- **ink-testing-library setState re-render timing** (US-005, 2026-06-14): `useState` updates triggered inside `useInput` handlers are async in React 19. `stdin.write('j')` fires the handler synchronously but the re-render (and the updated `lastFrame()`) happens as a scheduled macrotask. Tests that assert `lastFrame()` after state-changing keypresses need `await new Promise(r => setTimeout(r, 0))` (one macrotask tick) to let React flush. Tests that only assert synchronous side-effects (like injected `runTmux` calls) do not need the tick.
- **chalk.level and ANSI in ink-testing-library** (US-005, 2026-06-14): ink-testing-library's custom `Stdout` class has no `isTTY` flag, so chalk auto-detects color level 0 (no colors) when the test runner is not a TTY. To assert raw ANSI escape codes from `lastFrame()`, call `chalk.level = 3` in `beforeAll` and restore in `afterAll` (import `ColorSupportLevel` from chalk for the saved-value type). The 24-bit bg escape for `#4EBE7D` is `[48;2;78;190;125m` (the substring after the ESC byte). Arrow-key sequences passed to `stdin.write` must include the full ESC byte: down = `'[B'`, up = `'[A'`.
- **Ink 7 ESC pending-buffer (US-006, 2026-06-14)**: A lone `\x1b` byte written to ink-testing-library stdin is NOT immediately emitted as a keypress. Ink's `createInputParser` treats `\x1b` alone as a "pending escape" (could be the start of a multi-byte ANSI sequence) and schedules a 20ms flush via `setTimeout`. Tests that write `\x1b` and then assert `key.escape` behavior must wait > 20ms: use `await new Promise((r) => setTimeout(r, 50))` instead of the 0ms `tick()`. The handler-level check `if (key.escape)` is still correct; the delay is only a testing concern. Detection: if `await tick()` (0ms) leaves the escape state unchanged, the pending-escape buffer is the likely cause.
- **Test timeout with no-op sleepFn**: when injecting `sleepFn: () => {}` in tests for `waitForOrchestrator`, always pair it with a tiny `waitTimeoutMs` (5-10ms). The `while (Date.now() < deadline)` loop spins the CPU until the deadline expires; with a 5_000ms budget and a no-op sleep the test actually burns 5 real seconds and Bun's 5s per-test timeout kills it. Correct: `sleepFn: () => {}, waitTimeoutMs: 5`. (US-006, 2026-06-15.)
- **Single-hub dispatch invariant (CAM-55)**: `cam run` is the only dispatch hub. CLI subcommands (`cam plan`, `cam issue`, `cam next`, `cam ship`) are thin-proxies: detect the orchestrator session and inject the request via atomic `send-keys` (text + Enter in one call); if no session exists, bootstrap `cam run --no-attach` first and wait for the `.claude/.cam-orch-ready` marker before injecting. Workers run in a single reused titled 3rd pane (mutex: dispatch only when session has exactly 2 panes). Completion is push-report (worker writes a result file at exit), not pull-based scrollback polling. The idle-guarantee (ensuring the orchestrator is idle before the worker pushes its report) is its own story (US-008), not folded into the proxy.
- **@cam_label pane-labeling pattern (US-002, 2026-06-15)**: Label any pane before dispatch with `tmux set-option -p -t <paneId> @cam_label <value>`. The session-level `pane-border-format #{@cam_label}` (set in run.ts `setupPanes`) picks this up automatically for any pane added to the session later, including the worker pane. `set-option -p` is validated by tmux docs: pane-scoped `@`-prefixed user options are supported. In the supervisor (loop.ts), the label is set immediately before `respawn-pane -k`; in the review branch, before `reviewDispatch`. The label is best-effort (silent no-op if the pane is not yet open).
- **Mutex busy check in dispatch sites (US-009, 2026-06-15)**: Every thin-proxy dispatch site (plan, next, issue, review, ship) must call `paneCountMutex(sessionName, tmuxSpawnFn)` after the alive/bootstrap path and before `sendKeysWhenIdle`. If the result is `'busy'`, the command calls `printError('worker busy', 'blocked until the worker-pane closes')` and returns exit code 1 without sending any keys. Test helpers that fake `tmuxSpawnFn` must handle ALL `list-panes` format strings: `#{@cam_label}` (orchestratorAlive), `#{pane_index};#{pane_id}` (getOrchPaneId), `#{pane_current_command};#{@cam_label}` (isSessionStale), and `#{pane_id}` (paneCountMutex). If `#{pane_id}` is missing from the fake, `paneCountMutex` gets empty output, counts 0 panes, and returns `'busy'`, breaking the happy-path test. Use `paneMutexBusy` option in `makeFakeTmuxSpawn` to return 3 pane IDs (busy) vs 2 (available).
- **Idle-guarantee before send-keys (US-008, 2026-06-15)**: All thin-proxy commands (plan, next, issue, review, ship) must call `sendKeysWhenIdle` (src/tmux/dispatch.ts) instead of bare `tmuxSpawnFn send-keys`. `sendKeysWhenIdle` polls `capture-pane -p -t <paneId>` until `isOrchPaneIdle` returns true (no spinner glyph ⠋-⠏, no active tool-call glyph ◆ in the last 5 lines, and at least one line ending with `>` or `❯`). Fallback on timeout: log to stderr + still send (never block indefinitely). Default `idleTimeoutMs` is 5 000 ms; tests must inject `capturePaneFn: () => '> '` so the idle check passes immediately without a real tmux call. All test fake spawn fns (makeFakeTmuxSpawn) must handle `capture-pane` subcommand by returning idle content, or the idle-loop will spin for 5 s and hit Bun's per-test timeout.
- **Sidecar-supervisor invariant (US-FIX-001, 2026-06-15)**: the deterministic loop is a SIDECAR, not in-process and not absorbed by the LLM. Roles: `cam run` = sidecar host (spawns `runSupervisor` as a detached background process); the sidecar = the deterministic loop driver (gated on the `active` flag in `.claude/cam-loop.local.md`; holds the supervisor lock; carries the CAM-36 no-progress streak, CAM-44 dead-worker backoff, MAX_ITERATIONS, event log); the LLM orchestrator = human interface (narrates the sidecar's terminal report and routes plan/review/ship/issue), NOT the loop driver; `cam next` = trigger (a thin-proxy that flips `active:true`, never calls `runSupervisor` in-process); `scripts/cam/worker-report.json` = push completion signal (the worker writes it on exit; the sidecar reads it, no scrollback poll). The "orchestrator absorbs the loop" model is REJECTED: an LLM-driven loop loses every deterministic guard above.
- **Report-file completion detection (US-004, 2026-06-15)**: The supervisor poll loop uses an optional injected `ReadWorkerReport` dependency to detect worker completion instead of polling `capturePane + parseAnySentinel`. When `readWorkerReport` is injected and returns a non-null `WorkerReport`, the loop exits with `pollOutcome='sentinel'`. The state-primary outcome is still confirmed via `readWorkerOutcome` (prd.json + handoff.json). The fallback to `capturePane + parseAnySentinel` is preserved for backward compat when `readWorkerReport` is absent. `clearWorkerReport` should be called before `respawn-pane -k` to erase any stale report from the previous run (prevents false-positive on first poll tick). In next.ts, `readWorkerReport` reads `scripts/cam/worker-report.json` via `readFileSync`; `clearWorkerReport` uses `existsSync` + `unlinkSync` wrapped in try-catch (node:fs docs: `unlinkSync` throws ENOENT on missing file, `existsSync` returns false gracefully).
- **Sidecar dep-wiring in host.ts (US-FIX-002, 2026-06-15)**: The supervisor production wiring (spawn, capturePane, readPrd, writePrd, readHandoff, clock, reviewDispatch, writeSessionMarker, runGates, finalizeStory, ensurePushed, readWorkerTokens, readWorkerReport, clearWorkerReport, onProgress) lives in `src/supervisor/host.ts:buildSupervisorOptions(cwd)`. Never duplicate it inline; always call `buildSupervisorOptions`. The sidecar outer loop (gated on the `active` flag) lives in `src/supervisor/loop.ts:runSidecarLoop(opts)`. The production caller is `src/commands/sidecar.ts:runSidecar()`, registered as `cam sidecar` in index.ts (internal, not in help). `cam run` spawns it via `Bun.spawn(['cam','sidecar'], { stdio:['ignore', logFd, logFd] })` with the log fd pointing to `.claude/cam-supervisor.log`; the process is killed in the SIGINT/SIGTERM cleanup handler. `cam next` flips `active:true` by overwriting the state file (force:true) before its send-keys call. The lock is always released in a `finally` block so it is freed even when `runSupervisorFn` throws.
- **Agent-prompt self-hosting pattern (US-001, 2026-06-16)**: `templates/agents/` and `templates/commands/` are the SOURCE OF TRUTH for distributed agent prompts; `.claude/agents/` and `.claude/commands/` are the runtime mirrors materialized at `cam init` time. Any story that edits agent/command prompts MUST edit both the `templates/` copy and the `.claude/` copy, then run `bun run embed-vendor` to sync `src/vendor/_generated.ts`. Call this out in the commit message as "intentional self-hosting" so a later auditor does not flag it as harness drift. The `templatesContents` byte-parity test in `test/embedded.test.ts` will catch drift between `templates/` and the embedded copy.
- **ensureWorkerPane self-heal (CAM-57, 2026-06-16)**: A 2nd autonomous loop in a long-lived cam session can wedge because the worker pane was closed after the 1st loop (remain-on-exit off). The sidecar reads the marker once at boot and only does `respawn-pane -k` (no recreate): respawning a dead/missing pane is a no-op, so the worker never starts and `isPaneAlive` returns `false` forever. Fix: inject an `ensureWorkerPane` capability into `RunSupervisorOptions` (and `MakeReviewDispatchOptions`). Before every `respawn-pane -k` dispatch, call it: re-read the marker fresh (never cache the pane id from boot), call `isPaneAlive(currentId)`, and if dead call `openPaneInSession` to create a new pane, write the new marker, and return the new id. Backward compat: when the option is absent (older callers/tests), the static `workerPaneId` from opts is used unchanged. This is proved by a real-tmux integration test (`test/integration/ensure-worker-pane-selfheal.test.ts`) that kills a pane and asserts the self-heal creates a live one and rewrites the marker.
- **worker-report-fallback and handoff-string-coerced in readWorkerOutcome (US-001, 2026-06-17)**: `readWorkerOutcome` resolves the completed story via three signals in priority order: (1) handoff.json `lastCompletedStory.id`, (2) DONE sentinel from pane text, (3) `worker-report.json` (fallback when both are absent). Bare-string `lastCompletedStory` (e.g. `"US-001"` instead of `{id, title}`) is coerced to `{id}` and recorded as 'handoff-string-coerced' in the detail. The worker-report fallback is wired via `workerReportPath` in `ReadWorkerOutcomeOptions` and `RunSupervisorOptions`; the `fileReader` adapter in `loop.ts` serves the file via the injected `readWorkerReport` dep. These detail strings are tested by oracle grep.
- **tmux mangles TAB in -F output; key panes on @cam_label, not command (CAM-55 operator smoke, 2026-06-15)**: two real-tmux behaviors broke the whole introspection layer and were invisible to unit fakes (which encoded idealized output, so they matched the buggy code). (1) tmux converts a literal TAB (0x09) in a `-F` format string to `_` (0x5f) in its output: confirmed with `tmux display-message -p $'A\tB'` emitting `A_B`. NEVER use a TAB as a field separator in a tmux `-F` format; use `;` (preserved by tmux; command names, `@cam_label`s and pane ids never contain one). This had silently nulled `getOrchPaneId` (`#{pane_index}\t#{pane_id}`) and broken `isSessionStale` (`#{pane_current_command}\t#{@cam_label}`), so every thin-proxy failed with "Could not find orchestrator pane" and the C3 staleness check never matched. (2) The orchestrator pane runs claude UNDER a bash respawn-wrapper (CAM-23), so its `pane_current_command` is `bash`, never `claude`: `orchestratorAlive` must key on `@cam_label === 'orchestrator'`, never on the command (same lesson as isSessionStale). LESSON: a unit fake that returns the output the code EXPECTS cannot catch tool-real-behavior bugs. The tmux-introspection helpers are now guarded by a real-tmux integration test (`test/integration/tmux-introspect.test.ts`, skips when tmux is absent) that runs the helpers against an actual tmux session with real `@cam_label` panes. When adding/altering any `tmux -F` parse, add a case there.
- **Sidecar PID persistence pattern (US-001, CAM-67, 2026-06-17)**: `cam run` persists the sidecar process pid to `.claude/.cam-sidecar.pid` immediately after `Bun.spawn` returns (via `writeSidecarPid` in `src/supervisor/sidecar-pid.ts`). `cam stop` reads it via `readSidecarPid`, probes liveness with signal-0 (`process.kill(pid, 0)` in `sidecarPidAlive`), SIGTERMs only when alive, then removes the file (idempotent). The constant name is `SIDECAR_PID_FILE`. Injectable fakes (`sidecarPidReader`, `sidecarPidAliveFn`, `sidecarPidRemover`) keep the unit test free of real OS pids. Signal-0 throws `ESRCH` on a dead pid; `EPERM` means the process is alive but unpermissioned (treat as alive, conservative). `Bun.Subprocess.pid` is `readonly pid: number` (confirmed against Bun 1.3.x docs).
- **Per-session marker set + cam stop cleanup (US-002, CAM-67, 2026-06-17)**: `cam stop` removes all six per-session marker files idempotently (existsSync + unlinkSync in try/catch; absent markers are a no-op). The six markers are: `.claude/.cam-supervisor.lock` (SUPERVISOR_LOCK_FILE from `lock.ts`), `.claude/.cam-orch-session` (ORCH_SESSION_MARKER from `session.ts`), `.claude/.cam-worker-pane` (WORKER_PANE_MARKER from `session.ts`), `.claude/.cam-orch-ready` (ORCH_READY_MARKER from `bootstrap-wait.ts`), `scripts/cam/worker-report.json` (WORKER_REPORT_FILENAME from `worker-report.ts`), and `.claude/cam-loop.local.md` (STATE_FILE_PATH, local constant). Diagnostic-value files (cam-worker-events.jsonl, cam-supervisor.log, .cam-worker-*.session) are intentionally NOT removed. Rule: every new marker file introduced in the lifecycle MUST be (a) backed by a named export constant in its canonical module, and (b) added to the marker-removal loop in `performStop`. Never use bare string literals for marker filenames in stop.ts; the negative-grep oracle enforces this. `ORCH_SESSION_MARKER` was promoted from a bare string literal in run.ts to a named export on `src/tmux/session.ts` next to `WORKER_PANE_MARKER`; both the writer (run.ts) and the remover (stop.ts) import it from there.
- **Sidecar self-exit via startup-grace latch (US-003, CAM-67, 2026-06-17)**: `runSidecarLoop` accepts an optional `hasSessionFn: () => boolean` dep. On each idle tick, the loop calls it and tracks a `sessionSeen` one-shot latch: the first PRESENT result sets `sessionSeen = true`; a subsequent ABSENT result returns cleanly only if `sessionSeen` is already set. This prevents premature exit during the spawn-vs-session-creation race at startup (the session may not yet exist when the sidecar boots). The lock is NOT held during idle ticks, so the exit path needs no lock.release(). Production wiring in `sidecar.ts` builds a closure over `hasSession(projectSessionName(cwd), spawnFn)` using a `spawnSync`-backed `SpawnFn`. Tests inject a `hasSessionFn` array-sequence fake (no real tmux). The `sessionSeen` latch and "startup grace" text must appear in loop.ts to satisfy the file-assert oracles.
- **Scoped fallback kill for orphaned sidecars (US-006, CAM-67, 2026-06-17)**: `performStop` includes a two-phase sidecar-kill. Phase 1: read `.cam-sidecar.pid`, probe liveness (signal-0), SIGTERM if alive. Phase 2 (fallback, only when phase 1 found nothing alive): call `listProcessesFn()` which returns `ProcessRecord[]` with `{ pid, argv, cwd }`, filter via `matchesSidecarForProject(record, cwd)` (strict `record.cwd === projectCwd` equality, argv[0]==='cam', argv[1]==='sidecar'), SIGTERM matches. Injectable dep: `listProcessesFn?: ListProcessesFn` in `StopOptions`; production default uses `ps -eo pid,args` + `lsof -a -d cwd -p <pid> -F n`. Never use blanket `pkill cam sidecar` (kills foreign-project sidecars). Scoping primitive is strict equality, not prefix/substring. The `fallbackSidecarKilled: boolean` field in `StopReport` tracks whether the fallback found anything. Test file: `test/stop-sidecar-fallback.test.ts`.
- **Zero-dep vendor scripts: hand-rolled YAML parser (US-001, CAM-69, 2026-06-23)**: vendored scripts run in a tmpdir via `bun <script>` with no node_modules present. Bun auto-install kicks in for any bare-specifier import (e.g. `import yaml from 'js-yaml'`); if the package resolves to the wrong major (js-yaml@5 is ESM-only, no default export) the script crashes with `Missing 'default' export`. Fix: replace external deps with a hand-rolled parser. Scope for agent frontmatter: top-level `key: scalar` pairs (unquoted/quoted string, int, float, bool, null) plus block-sequence lists (`  - item` lines under a key with empty value). The parser returns a 0-indexed line within the frontmatter text on error; add +2 to convert to a 1-indexed file line (matching the old js-yaml `mark.line + 2` semantics). `$` in grep patterns is regex end-of-line; escape as `\$` when checking for literal `$` in template literals. After any vendor edit: `bun run embed-vendor` then `bun run embed-vendor:check`.
- **Injectable onResults callback for structured CLI output (US-004, CAM-59, 2026-06-23)**: when a CLI script needs both human-readable output (stdout lines) and machine-readable output (JSON), use an `onResults?: (results: T[]) => void` injectable on the options object. The caller supplies a callback (e.g. write to a file, write to stdout, capture in test). Tests inject a capture function to assert shape without touching the filesystem. The CLI entrypoint supplies a file-writer when the `--json` flag is present. This keeps the runner function pure and testable. For the CI summary pattern: write to a well-known filename (e.g. `gate-results.json`) in cwd; the follow-up `if: always()` step reads it with `jq` and appends a markdown table to `$GITHUB_STEP_SUMMARY`. Add the output file to `.gitignore` so it is not accidentally committed.
- **js-yaml named import (US-003, CAM-69, 2026-06-23)**: always use `import { load } from 'js-yaml'` (named import), never `import yaml from 'js-yaml'` (default import). js-yaml v4.1.1 has no default export (`typeof y.default === 'undefined'`); a default import only works because Bun/CJS interop injects one at runtime. js-yaml v5 is ESM-only with no default export at all, so the default import crashes with "Missing default export". Named `load` exists in both v4 and v5, making it the forward-compatible form.
- **Gate-spine convention (US-005, CAM-59, 2026-06-23)**: all quality gates are declared as entries in the `GATES` manifest in `scripts/check-all.ts`. New gates are added there (never invoked ad-hoc in CI). The CI workflow calls only `bun run check:all` (the spine); `ci-parity` (`scripts/check-ci-parity.ts`) enforces that `ci.yml` and the GATES manifest stay in sync. If you need a new gate: (1) add it to `GATES` in `check-all.ts`; (2) do NOT add a separate step in `ci.yml` for it (the spine picks it up automatically); (3) run `bun run check:ci-parity` locally to confirm parity. See `docs/recovery-runbook.md` CAM-59 section for debugging parity failures.
- **Real-git integration test pattern (US-004, CAM-72, 2026-06-23)**: unit fakes for spawnFn (see test/ship-finalize.test.ts) cannot catch git-behavior bugs (the fake records the call and returns success regardless of whether real git would refuse). Add a real-git integration test in test/integration/ for any function that calls git rm / git commit on user-modified files. Pattern: `mkdtempSync` a fresh repo in tmpdir, `git init`, `git config user.email/user.name` (required for commit), write+stage+commit the baseline files, then overwrite to simulate the dirty state, run the function with a `realSpawnFn` wrapper over `spawnSync`, and assert with real `git ls-files` / `git status --porcelain` / `git log -1 --format=%s`. Register dirs in an `afterEach` cleanup array (`rmSync` with `{ recursive: true, force: true }`). Skip when git is absent via `spawnSync('git', ['--version'], { stdio: 'pipe' }).status === 0` + `test.skipIf(!gitAvailable)`.
- **finalizeCycleClose hardening pattern (US-005, CAM-72, 2026-06-23)**: three idempotency/safety guards must be present: (a) wrap `readPrd()` in try-catch; ENOENT means cycle already closed, return `{ noOp: true }` with a `printHint` instead of crashing; (b) when `issue_system == 'none'` and the issue entry is absent from issues.local.json, call `printError` and throw (hard failure: rm+commit must NOT silently proceed with a corrupt issue log); (c) after all `git rm` + `git add` calls, run `git diff --cached --quiet`; exit 0 means nothing staged, skip commit (prevents "nothing to commit" git error). In recording-spawn fakes, default `diffCachedStatus` to 1 (staged = commit proceeds); override to 0 in tests that assert noOp. AC4 (second invocation = no-op) is a corollary of guard (a): the first run removes prd.json via `git rm`, so the second run finds it absent.
- **Pane worker vs Task subagent (when to use which, architecture note 2026-06-16)**: the cam agents split by WHO DRIVES them, not by being "agents". TWO run as interactive `claude` sessions in a tmux pane: the **implementer** and the **reviewer** (the reviewer reuses the same titled worker pane, re-labeled, via `review.ts`). Pane is correct for both because they are UNATTENDED LOOP WORKERS dispatched by the deterministic sidecar (`respawn-pane -k` into the single titled worker pane): (1) the sidecar (TS code), not an LLM, owns scheduling, retry, and limits (MAX_ITERATIONS, no-progress streak CAM-36, dead-worker backoff CAM-44, supervisor lock); (2) crash isolation plus independent kill/respawn; (3) the operator can watch and attach the pane live; (4) it is a full dev session that commits, pushes, and runs gates; (5) the subscription rule (CAM-42) forces interactive TUI, not headless `-p`. TWO run as Task subagents (`Task(subagent_type=...)`) inside the interactive `/cam-plan` flow: the **planner** (Step 7) and the **auditor** (Step 8). Task is correct for them because they are PLAN-TIME HELPERS orchestrated by the LLM during an operator-approved conversation (scope approval at Step 6, the bounded audit loop at Step 8), are ephemeral, and their output is consumed immediately by the orchestrator. They need none of the pane benefits, and a pane would only inherit the tmux-lifecycle bug class (CAM-40/43/57) for no gain. The **orchestrator** is pane 0 itself (the root persona of `cam run`, never Task-invoked). DIVIDING LINE: a deterministic-loop unattended worker is a pane; an LLM-orchestrated interactive helper is a Task subagent. Do not convert planner/auditor to panes, and do not convert implementer/reviewer to Task subagents (the latter would force an LLM-driven loop and lose every deterministic guard, the model CAM-55 rejected).
- **Oracle-friendly manifest design (US-001, CAM-59, 2026-06-23)**: when a gate-manifest array is checked by grep-based oracles (e.g. `grep -q 'tsc --noEmit' scripts/check-all.ts`), define each entry as a full command string (e.g. `'bunx tsc --noEmit'`) and split at runtime via a small helper (`g(name, cmdStr)` in check-all.ts splits on space). This makes the oracle grep match the literal command while keeping the runtime representation as `{ cmd, args[] }`. The split-at-runtime approach is only for commands that are clean space-separated tokens; do NOT use it for commands with quoted args or embedded spaces.
- **bun test --coverage output format (US-004, CAM-60, 2026-06-23)**: the text reporter emits columns `% Funcs | % Lines` (in that order; no statements/branches columns). The aggregate row header is `All files`. Parse with regex `^All files\s*\|\s*([\d.]+)\s*\|\s*([\d.]+)`. Coverage output goes to stderr (not stdout), so capture both streams in the production adapter. When the coverage gate runs inside `bun run check:all`, bun test executes twice (once for the `test` gate, once for `coverage`). This is expected and by design: the coverage gate is the only consumer of `--coverage` output.

- **Debt-marker gate self-reference gotcha (US-003, CAM-60, 2026-06-23)**: the gate script itself must not contain a bare `TODO/FIXME/HACK/XXX` token followed by space or colon, or it trips its own gate. When documenting the list of target markers in a comment like `// Scans for TODO/FIXME/HACK/XXX markers`, the `XXX` at the end is followed by a space and matches the regex. Fix: wrap in parens so `XXX` is followed by `)` which is not `\s|:`, e.g. `// Scans for (TODO/FIXME/HACK/XXX) markers`. The regex is `(?<!-)\b(TODO|FIXME|HACK|XXX)\b(?=[:\s])`. Negative lookbehind `(?<!-)` correctly excludes `US-XXX` and `CAM-XXX` identifier forms (hyphen precedes `XXX`). EXCLUDED_DIRS are pinned in the script: `vendor/`, `node_modules/`, `claude-code-harness/`, `dist/`.
- **biome 2.x lint-only config pattern (US-001, CAM-60, 2026-06-23)**: `linter.rules.recommended: false` is deprecated in biome 2.x (use `preset: "none"` instead) but still accepted and only emits an `i` info diagnostic (NOT a warning/error), so `--error-on-warnings` does NOT fail on it. Keep `recommended: false` when oracles check `.linter.rules.recommended == false`. The per-file grandfather pattern uses `overrides[].includes: ["concrete/path.ts"]` with `linter.rules.complexity.<ruleName>: "off"`. Catch-all globs (`**`, `**/*.ts`, etc.) must NOT appear in includes. A stale `biome-ignore` suppression for a rule that is NOT enabled becomes a `suppressions/unused` WARNING (affected by `--error-on-warnings`): remove the comment or enable the rule. Run `bunx biome lint --max-diagnostics 200 2>&1` to see the full violator list when max-diagnostics is hit.
- **Biome cognitive complexity: use factory/helper extraction not grandfather (US-002, CAM-60, 2026-06-23)**: when a function's cognitive complexity exceeds 15, prefer extracting default adapters as `makeDefault*` top-level factory functions AND extracting inner loop/if bodies into named helper functions (e.g. `checkSizeCeilings`, `checkDiffTrackerRef`). This brings the main orchestrator function well under the limit. Prefer refactoring over adding a new per-file `noExcessiveCognitiveComplexity: "off"` override, since the override masks future growth. The `??` null-coalescing operator counts as +1 complexity each in biome; four `??` defaults in one function can push complexity from 8 to 12 before adding any loops.
- **knip grandfathering strategy (US-005, CAM-60, 2026-06-23)**: to introduce a green knip gate on an existing codebase with many findings, use a combination of: (1) broad entry points including `test/**/*.ts` and `scripts/**/*.ts` so test-consumed exports are reachable; (2) `ignore` for specific unused files; (3) `ignoreBinaries` for external tools (claude, tmux, ps, lsof); (4) `exclude: ["exports","types","duplicates"]` to grandfather the bulk of export/type issues without deleting code. This satisfies the "green today, prevents NEW dead files" goal while leaving tightening to future stories. knip "configuration hints" (suggestions to remove redundant ignore entries) are informational-only and do not affect the exit code; leave the ignore entries in place as explicit documentation of what was grandfathered. `content.split('\n').length` (the file-size script's counter) is always `wc -l + 1` for files with a trailing newline: set budgets accordingly.
- **Backward-compatible TOML reader for scalar-to-section evolution (US-003, CAM-53, 2026-06-24)**: when a TOML key transitions from a scalar form (`backend = "claude"`) to a section form (`[backend]\nname = "claude"`), update the reader to handle both: check `typeof value === 'string'` first (scalar), then `typeof value === 'object'` for the section form (`value['name']`). This preserves backward compat with existing config files while consuming newly written section-form configs. Applied to `readBackend` in `src/config/models.ts`.
- **jscpd v5 config format (US-006, CAM-60, 2026-06-23)**: jscpd v5 (Rust rewrite) reads the same `.jscpd.json` as v4. Keys: `threshold` (number), `reporters` (array of strings, e.g. `["threshold"]`), `ignore` (array of globs). The `threshold` reporter exits 0 when duplication is at or below the threshold and exits 1 (with an error message) only when duplication exceeds it: safe as a ratchet gate. Paths to scan are positional CLI args (not a config key), so the gate command must pass them explicitly: `bunx jscpd@5 --config .jscpd.json src scripts`. The `reporters: ["threshold"]` + threshold combo produces silent output on pass and a one-line error on fail, which is CI-friendly. Confirmed on jscpd@5 with src/+scripts/ (3.87% actual duplication, threshold 4%).

- **Ratchet gate pattern (US-007, CAM-60, 2026-06-23)**: ratchets enforce snapshot-on-adopt, change-direction-locked. Snapshot: the metric ceiling/floor is captured in a JSON budget file (e.g. `file-size-budget.json`, `coverage-budget.json`) at the point the gate is adopted. Change-direction-locked: improvement (lower size, higher coverage, lower dup) is always free; degradation (raise size ceiling, lower coverage floor, raise dup threshold) requires a tracker reference (`CAM-NNN`, `#N`, or `https://`) in the staged diff of the budget file. The check reads `git diff --cached <budget-file>`, so the tracker ref must be staged, not just present in the working tree. jscpd has no built-in tracker-ref check: the tracker-ref convention for `.jscpd.json` changes is enforced by code review and the commit message, not by the gate script. When a story legitimately degrades a ratchet metric: file a tracker issue first, include the ref in the budget diff, then implement. Recovery: see `docs/recovery-runbook.md` scenario (j). Coverage floors snapshot the measured value but the gate compares with a small tolerance epsilon (0.5pp) to absorb cross-environment jitter, since the CI runner measures slightly different coverage than local (CAM-60, found on PR #66).
- **Spawn-resolution emitter pattern (US-007, CAM-53, 2026-06-24)**: `src/logging/spawn-resolution.ts` exports `emitSpawnResolution({ phase, model, backend, writeEvent?, emitNotice? })`. Call it at every cam-controlled spawn (orchestrator in run.ts, implementer in loop.ts, reviewer in review.ts) immediately before the `respawn-pane -k` tmux call. Injectable seams: `writeEvent` (capture in tests, omit in production for stderr-only mode), `emitNotice` (capture the codex guard notice in tests without hitting real stderr). Codex guard: when `backend === 'codex'`, `CODEX_GUARD_NOTICE = 'codex backend not yet wired (CAM-54)'` is emitted via `emitNotice` (default: `process.stderr.write`). Guard is informational, never aborts the spawn. Test files live under `test/logging/` mirroring `src/logging/`.
- **[models]/[backend] config surface and read-at-spawn invariant (US-008, CAM-53, 2026-06-24)**: per-phase models are stored under `[models]` in `scripts/cam/project.toml` (keys: orchestrator, planner, auditor, implementer, reviewer, ship); the backend is stored under `[backend]` as `name = "<value>"`. Both are read at spawn time via `readPhaseModel(phase, configPath)` and `readBackend(configPath)` from `src/config/models.ts`; both fall back to `DEFAULTS` on any read/parse error so the loop is never blocked by a misconfigured toml. Inspect the resolved values non-interactively with `cam config --show` (implemented via `printConfigShow` in `src/commands/config.ts`, injectable writer seam for tests, no Ink/TTY required). Reset to defaults: remove the `[models]` and `[backend]` sections from `project.toml`. Recover from a typo'd model: run `cam config` (interactive wizard) or hand-edit the key and verify with `cam config --show`.
- **Frontmatter model: rewriter pattern (US-006, CAM-53, 2026-06-24)**: in-session phases (planner, auditor, ship) run as Task subagents or slash steps where `cam` cannot pass `--model` on the command line; the chosen model must reach them via the `model:` frontmatter line of their `.claude/` runtime files.
